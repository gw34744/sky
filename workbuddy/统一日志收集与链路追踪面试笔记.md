# 统一日志收集 + 链路追踪 面试笔记

> 对应简历技术点：**统一日志规范（Logback）+ MDC 链路追踪 ID**，可选进阶 **SkyWalking / Spring Cloud Sleuth**。
> 本文档配合代码落地：`logback-spring.xml`、`TraceIdUtil`、`TraceIdFilter`、`GlobalExceptionHandler`。

---

## 一、问题背景：为什么需要「统一日志 + 链路追踪」

一个外卖订单从「用户下单 → 支付回调 → MQ 来单提醒 → WebSocket 推送给骑手 → 接单/出餐/完成」会横跨：

- 多个 Controller / Service
- 异步 MQ 消费者（`OrderNotifyListener`）
- WebSocket 推送（`WebSocketServer`）
- 多个应用实例（水平扩容后）

**没有链路追踪时的痛点：**

1. 日志散在各处、格式不一，出问题时像大海捞针；
2. 一次请求在并发下与其它请求的日志交错在一起，**无法区分哪行日志属于哪次请求**；
3. 高并发时同步写日志阻塞业务线程，拖垮吞吐（访问通道承载能力）；
4. 日志无归档策略，磁盘被无限撑大。

**目标：** 给每次请求（及其触发的所有异步链路）打上一个全局唯一 `traceId`，所有日志都带这个 ID，于是可以 **grep 一个 traceId 就能还原整条调用链**。

---

## 二、核心概念：MDC（Mapped Diagnostic Context）

MDC 是 SLF4J 提供的一个**线程级（ThreadLocal 实现）**的日志上下文容器，可以在日志格式中用 `%X{key}` 取出来。

```java
MDC.put("traceId", "abc123");   // 注入
log.info("下单成功");            // 日志自动带 traceId=abc123
MDC.remove("traceId");          // 必须清理
```

**三个必须牢记的坑：**

| 坑 | 后果 | 解法 |
|----|------|------|
| 不清理 MDC | Tomcat 线程池复用线程，下一个请求**串号**（拿到别人的 traceId） | `finally` 里 `MDC.remove` |
| 跨线程丢上下文 | MQ 消费、`@Async`、线程池里 traceId 丢失 | 手动把 MDC 值传给子线程再 `put` |
| 只用 `%X{}` 但没 `put` | 日志里 `[traceId:]` 为空，形同虚设 | 入口 Filter 统一注入 |

---

## 三、本项目的实现方案（三层）

### 1. TraceIdUtil（sky-common）

```java
public static String generateTraceId() {
    return UUID.randomUUID().toString().replace("-", ""); // 32 位
}
```

- `TRACE_ID = "traceId"`：MDC 的 key；
- `TRACE_ID_HEADER = "X-Trace-Id"`：透传上游的请求头。

### 2. TraceIdFilter（sky-server，@Order(HIGHEST_PRECEDENCE)）

用 **Filter 而非 Interceptor**，因为 Filter 在 Servlet 容器最外层，能覆盖到拦截器之前、静态资源、错误页等**所有**进入容器的请求。

```java
String traceId = req.getHeader("X-Trace-Id"); // 上游有则透传
if (traceId == null) traceId = TraceIdUtil.generateTraceId();
MDC.put("traceId", traceId);
resp.setHeader("X-Trace-Id", traceId);        // 回写，前端报错时能带 traceId
try {
    chain.doFilter(req, resp);
} finally {
    MDC.remove("traceId");                      // 关键：清理防串号
}
```

**透传的意义：** 生产环境前面有 Nginx / 网关，如果它们也生成 traceId 并通过 `X-Trace-Id` 传下来，本服务直接复用，就能做到**跨服务**串联（这是分布式链路追踪的雏形）。

### 3. logback-spring.xml（统一格式 + 归档 + 异步）

统一格式（所有日志都带 traceId）：

```
%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] [traceId:%X{traceId}] %logger{40} - %msg%n
```

输出策略：

| Appender | 作用 |
|----------|------|
| CONSOLE | 控制台输出（dev 环境） |
| FILE_ALL | 全量日志滚动文件（按天 + 100MB 切分，保留 30 天，总量 5GB） |
| FILE_ERROR | ERROR 单独文件，便于告警 |
| ASYNC_FILE_* | **异步包装**，独立线程池写文件，不阻塞业务线程 |

环境差异化（`<springProfile>`）：

- **dev**：控制台 + 文件全量 + 打印 MyBatis SQL（`com.sky.mapper` 级别 DEBUG）；
- **prod**：只落文件、关闭控制台、SQL 不打，控制日志量与磁盘。

## 四、异步链路如何保证 traceId 不丢（重要考点）

MDC 基于 ThreadLocal，**异步线程天然拿不到主线程的 traceId**。本项目有两处异步：

1. **MQ 消费者**（`OrderNotifyListener`）：RabbitMQ 的监听线程不在请求线程里，需要显式传递；
2. **@Async / 自定义线程池**：子线程同样拿不到主线程 MDC。

**通用解法（面试必答）：**

```java
// 主线程取出
String traceId = MDC.get("traceId");
// 提交到线程池时显式传参
executor.submit(() -> {
    MDC.put("traceId", traceId);
    try { /* 业务 */ }
    finally { MDC.remove("traceId"); }
});
```

### 本项目已落地的三种跨线程传递（代码真实实现）

**① MQ 消费者——消息头透传 traceId**

- 发送端 `OrderServiceImpl.paySuccess`：`convertAndSend` 用 `MessagePostProcessor` 把当前线程 traceId 写入消息头 `X-Trace-Id`：
  ```java
  rabbitTemplate.convertAndSend(exchange, routingKey, msg, m -> {
      m.getMessageProperties().setHeader(TraceIdUtil.TRACE_ID_HEADER, TraceIdUtil.getTraceId());
      return m;
  });
  ```
- 消费端 `OrderNotifyListener.onOrderComing`：从消息头取出 traceId → `MDC.put` → 业务 → `finally MDC.remove`。

**② @Async 线程池——TaskDecorator 统一复制（Spring 官方推荐，一处配置全局生效）**

- `MdcTaskDecorator`：实现 `TaskDecorator`，提交任务时先取主线程 traceId，子线程执行前恢复、执行后清理；
- `AsyncConfiguration`：`@EnableAsync` + 定义 `asyncExecutor` 线程池，`setTaskDecorator(new MdcTaskDecorator())`；
- 效果：以后任何 `@Async("asyncExecutor")` 方法的日志都自动带 traceId，业务代码零侵入。

**③ 定时任务——独立线程池（SchedulingConfiguration）**

定时任务（`@Scheduled`）本身无请求上下文，不需要 traceId，但已配置独立线程池并行执行，避免单线程串行。

## 五、进阶：SkyWalking / Spring Cloud Sleuth 说明

自己手写 MDC 只能解决**单服务内**的日志串联；当服务拆分成微服务、调用跨进程时，需要专业的 **分布式链路追踪** 组件。二选一：

### Spring Cloud Sleuth（已停止独立维护，合并进 Micrometer Tracing）

- 原理：为每个请求生成 **TraceId（全局）+ SpanId（单段）**，通过拦截器自动注入到日志 MDC 和 HTTP 头（`X-B3-TraceId` / `X-B3-SpanId`）中；
- 优点：**零侵入**，加依赖即用，日志里自动出现 traceId/spanId；
- 配合 Zipkin 做调用链可视化、耗时分析。

### SkyWalking（国内主流，推荐）

- 原理：**Java Agent 字节码增强**，`-javaagent:skywalking-agent.jar` 启动，**对业务代码完全无侵入**；
- 能力：调用链拓扑图、慢请求分析、性能指标（QPS/RT）、告警；
- 组件：OAP（收集分析）+ UI（展示）+ Agent（探针）；
- 优点：不依赖 Zipkin，自带存储（ES/H2），适合 Spring Boot 单体 → 微服务全链路。

**与本项目的关系：** 手写的 `traceId + X-Trace-Id` 是「轻量版链路追踪」，适合单体项目快速落地；若未来服务拆分或需要调用链可视化，再平滑升级到 SkyWalking（改启动参数即可，业务代码不动）。

## 六、面试高频问答

**Q1：为什么用 Filter 注入 traceId，不用 Interceptor？**
Filter 在 Servlet 容器最外层，能覆盖拦截器之前、静态资源、错误页等所有请求；Interceptor 是 Spring MVC 层，覆盖不到 `@ControllerAdvice` 之前的异常和静态资源。

**Q2：MDC 为什么能实现链路追踪？底层是什么？**
MDC 底层是 `ThreadLocal`，每个线程一份日志上下文。一次请求从头到尾在同一个 Tomcat 线程里执行，所以该线程打的所有日志都带同一个 traceId；配合 `%X{traceId}` 占位符自动输出。

**Q3：traceId 会串号吗？什么情况会串？怎么避免？**
会。Tomcat 线程池复用线程时，如果上个请求没 `MDC.remove`，下个请求会读到残留的 traceId。解法：`finally` 里 `MDC.remove`；跨线程要手动复制上下文。

**Q4：异步线程（MQ / 线程池）日志为什么没有 traceId？**
ThreadLocal 不跨线程。解法：显式传参 + 子线程 `MDC.put`；或 Spring `TaskDecorator` 统一复制。

**Q5：为什么不直接同步写日志，要 AsyncAppender？**
高并发下磁盘 IO 慢，同步写会阻塞业务线程，拖垮吞吐。AsyncAppender 用独立线程 + 队列异步写，业务线程只入队即返回。代价是极端情况下（队列满 + 进程崩溃）可能丢少量日志，可设 `neverBlock=false` + 保留 WARN/ERROR 兜底。

**Q6：日志文件无限增长怎么办？**
`SizeAndTimeBasedRollingPolicy`：按天 + 按大小（100MB）双重滚动，`maxHistory=30` 自动删 30 天前，`totalSizeCap=5GB` 总量上限。

## 七、落地文件清单

| 文件 | 作用 |
|------|------|
| `sky-server/src/main/resources/logback-spring.xml` | 统一格式 + 归档 + 异步 + 环境差异化 |
| `sky-common/.../context/TraceIdUtil.java` | traceId 生成/读取常量 |
| `sky-server/.../filter/TraceIdFilter.java` | 入口注入/透传/清理 MDC |
| `sky-server/.../config/MdcTaskDecorator.java` | @Async 线程池跨线程复制 MDC |
| `sky-server/.../config/AsyncConfiguration.java` | @EnableAsync + asyncExecutor 线程池 |
| `sky-server/.../listener/OrderNotifyListener.java` | MQ 消费端从消息头恢复 traceId |
| `sky-server/.../service/impl/OrderServiceImpl.java` | MQ 发送端把 traceId 写入消息头 |
| `GlobalExceptionHandler.java` | 异常日志带堆栈 + traceId 上下文 |
| `application.yml` | 补充 `spring.application.name`（日志文件名前缀） |

**验证方式：** 启动后请求任意接口，观察响应头 `X-Trace-Id`，再看 `logs/sky-take-out.log`，同一次请求的所有日志（含异常）都带同一个 `traceId`，`grep traceId` 即可还原整条链路。
