# 支付回调幂等性面试笔记

> 支付回调是支付系统里**最核心、最不能出错**的环节。微信/支付宝在支付成功后，
> 会通过异步回调通知商户，但这个通知**不保证只发一次**——网络抖动、超时重试、
> 消息队列重投，都会导致同一个支付结果被推送多次。

---

## 一、为什么支付回调必须幂等

### 回调的三大特性（决定了必须幂等）

1. **不保证送达一次**：微信回调若 5 秒内没收到商户的"成功"应答，会**按 15s/15s/30s/3m/10m/20m/30m/30m/30m/60m/3h/3h/3h/6h/6h** 的间隔重试，最多重试多次。
2. **异步**：回调是微信服务器主动发起，**没有用户登录态**，也拿不到 ThreadLocal 里的 userId。
3. **可能乱序/重复**：极端情况下同一笔订单的回调可能重复到达。

### 不幂等的后果

- **重复更新订单**：本来"待接单"的订单被重复置为"待接单"，看似无害，但会**重复触发业务**；
- **重复推送来单提醒**：商家端 WebSocket 被刷屏，同一个订单弹多次；
- **更严重的**（在真实电商）：重复发货、重复加积分、重复发券。

---

## 二、本项目原来的三个缺陷

我在改造前发现 `paySuccess` 有 **3 个严重问题**：

### 缺陷 1：依赖登录态（致命 bug）

```java
Long userId = BaseContext.getCurrentId();  // 回调场景下是 null！
Orders orderDB = orderMapper.getByNumberAndUserId(outTradeNo, userId);
```

支付回调是微信服务器主动调用的，**根本没走 JWT 拦截器**，`ThreadLocal` 里没有 userId，
`getByNumberAndUserId(outTradeNo, null)` 永远查不到订单，直接 NPE。

> 这是"照着视频抄"很容易踩的坑——`paySuccess` 这个方法既被**用户下单后的主动查询**调用，
> 又被**微信回调**调用，而只有前者有登录态。

### 缺陷 2：无幂等判断

微信重复回调时，每次都无脑 `update` 状态 + `sendToAllClient` 推送，导致重复处理。

### 缺陷 3：没有交易号字段

`Orders` 实体没有 `transactionId`，无法记录微信交易号，也就无法用交易号判重/对账。

---

## 三、我的修复方案

### 1. 新增 `transaction_id` 字段

```sql
ALTER TABLE orders ADD COLUMN transaction_id varchar(64)
    DEFAULT NULL COMMENT '微信支付交易号' AFTER number;
```

### 2. 新增按订单号查询（不依赖 userId）

```java
// OrderMapper.java
Orders getByNumber(@Param("orderNumber") String orderNumber);
```

```xml
<!-- OrderMapper.xml -->
<select id="getByNumber" resultType="com.sky.entity.Orders">
    select * from orders where number = #{orderNumber};
</select>
```

### 3. 改造 paySuccess（核心）

```java
public void paySuccess(String outTradeNo, String transactionId) {
    // 按订单号查（不依赖 userId，因为回调无登录态）
    Orders orderDB = orderMapper.getByNumber(outTradeNo);
    if (orderDB == null) {
        throw new OrderBusinessException(MessageConstant.ORDER_NOT_FOUND);
    }

    // 幂等判断：已支付 → 重复回调，直接返回
    if (Orders.PAID.equals(orderDB.getPayStatus())) {
        log.info("重复回调，忽略：{}", outTradeNo);
        return;
    }

    // 更新状态 + 记录交易号
    Orders orders = Orders.builder()
            .id(orderDB.getId())
            .status(Orders.TO_BE_CONFIRMED)
            .payStatus(Orders.PAID)
            .transactionId(transactionId)
            .checkoutTime(LocalDateTime.now())
            .build();
    orderMapper.update(orders);

    // 推送来单提醒
    webSocketServer.sendToAllClient(...);
}
```

## 四、幂等的常见实现方案（面试扩展）

### 方案对比

| 方案 | 原理 | 适用场景 |
|------|------|----------|
| **状态判断（本项目）** | 查订单状态，已处理则跳过 | 状态流转简单、能通过状态区分 |
| **唯一约束 + 数据库** | transaction_id 加唯一索引，重复插入报错 | 需要强一致、有独立流水表 |
| **Redis 分布式锁 + setIfAbsent** | 回调先抢锁，抢不到说明在处理 | 高并发、处理耗时长的场景 |
| **token / 流水号去重** | 每个请求带唯一流水号，Redis 判重 | 通用接口防重 |

### 本项目为什么用"状态判断"就够了

- 订单状态机简单：`待付款 → 待接单` 是单向的；
- 判断 `payStatus == PAID` 就能可靠识别"是否已处理"；
- 无需引入分布式锁，代码最简单、最易理解。

### 如果要更严格（面试加分点）

可以给 `transaction_id` 加**唯一索引**，配合 `INSERT ... ON DUPLICATE KEY UPDATE` 或独立的
`支付流水表`，做到数据库层面的强幂等。

## 五、一页速记

| 问题 | 答案要点 |
|------|----------|
| 为什么回调要幂等？ | 微信回调不保证只发一次，会重试，重复处理会重复推送/发货 |
| 回调有登录态吗？ | 没有，微信服务器主动调用，拿不到 ThreadLocal 的 userId |
| 怎么判重？ | 查订单 payStatus，已支付（PAID）就是重复回调，直接 return |
| 交易号有什么用？ | 记录微信 transactionId，用于幂等判断、对账、售后查询 |
| 更严格的方案？ | transaction_id 唯一索引 + 支付流水表 + 分布式锁 |
