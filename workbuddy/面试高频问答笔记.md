# 面试高频问答笔记：多线程 / 超卖 / 缓存击穿 / 幂等性

> 本文配合「苍穹外卖」项目使用，讲清楚每个概念「是什么、项目里落地在哪、怎么答」。
> 核心原则：**简历写的是「学习/了解」，面试要能把「概念」和「项目落地」对上号。**

---

## 一、多线程（抢占、睡眠、锁竞争）

### 概念
- **线程抢占**：多线程并发执行时，由 CPU 调度器决定谁先执行，无法保证先后顺序，因此共享资源需要同步；
- **睡眠**：`Thread.sleep()` 让出 CPU 但**不释放锁**；
- **锁竞争**：多个线程争抢同一把锁，未抢到的进入阻塞队列等待。

### 本项目落地情况（诚实版）
- 项目里**没有**真正的多线程并发控制（没有 synchronized / ReentrantLock / 线程池）；
- 唯一相关的是 `ThreadLocal`（`BaseContext`），但它**不是**并发控制，而是「每个线程一份独立副本」的线程隔离，用来在拦截器里存当前登录用户 id，避免每个方法都传参；
- 本次新增的**缓存击穿防护**里，用到了「自旋 + `Thread.sleep(50)`」的等待重试逻辑，这是「睡眠 + 抢占」思想的一个真实落地点。

### 面试答题思路
> "项目里我用 ThreadLocal 做登录用户的线程隔离；在缓存击穿防护里，我用自旋等待 + sleep 让抢不到锁的线程短暂退避后重试，避免大量请求同时打库。另外我系统学习过 synchronized / ReentrantLock / volatile / 线程池，理解锁升级、AQS、CAS 这些机制。"

### 易被追问的点
- `Thread.sleep` 和 `Object.wait` 的区别：sleep 不释放锁，wait 释放锁且需在 synchronized 内调用；
- ThreadLocal 内存泄漏：key 是弱引用，value 是强引用，用完要 `remove()`（本项目拦截器里 `afterCompletion` 有 remove）。

## 二、超卖

### 概念
并发下单时，库存扣减操作「读库存 → 判断 → 写回」不是原子操作，导致多个请求都读到同一份库存并成功扣减，最终卖出的数量超过实际库存。

### 本项目落地情况（诚实版）
- **本项目没有库存概念**：`Dish` / `Orders` 实体里都没有库存字段，外卖业务是「下单即生成订单」，不涉及商品数量扣减，所以**超卖问题在这个项目里天然不存在**；
- 但这不代表可以不懂——面试官可能问「如果是电商/秒杀，你怎么防超卖」。

### 面试答题思路
> "我这个外卖项目没有库存扣减，所以不存在超卖。但我理解超卖的本质是「检查 + 扣减」非原子，防超卖一般有几层：① SQL 层用 `update stock set stock = stock - 1 where stock > 0` 乐观扣减；② 加乐观锁（version 字段）或悲观锁（select for update）；③ Redis 预扣减 + Lua 脚本保证原子性；④ 终极方案是消息队列削峰 + 事务。"

### 易被追问的点
- 悲观锁 vs 乐观锁的适用场景、优缺点；
- Redis 扣减为什么用 Lua（脚本保证原子执行）；
- 数据库 `where stock > 0` 这行 SQL 为什么能防超卖。

## 三、缓存击穿

### 概念（先分清三个词）
- **穿透**：查一个缓存和数据库都不存在的 key，每次都打到 DB → 空值缓存 / 布隆过滤器；
- **击穿**：某个**热点 key** 在过期瞬间，大量并发请求同时打到 DB → 互斥锁 / 逻辑过期；
- **雪崩**：大量 key 同一时间过期，请求集中打到 DB → 过期时间加随机值 / 集群高可用。

### 本项目落地情况（本次已实现）
- 改造 `user/DishController#list`，加入了**互斥锁（setIfAbsent）+ 自旋重试**的击穿防护：
  1. 查缓存未命中 → 尝试 `setIfAbsent(lockKey, "1", 10s)` 抢锁；
  2. 抢不到锁 → `Thread.sleep(50)` 后重读缓存，缓存重建好了就直接返回；
  3. 抢到锁 → 二次校验（double check）→ 查库 → 写缓存 → `finally` 释放锁。

### 面试答题思路
> "菜品是热点数据，缓存失效瞬间可能被击穿。我用 Redis 的 setIfAbsent 做互斥锁：只有一个线程能拿到锁去查库重建缓存，其他线程自旋等待、重读缓存。这样把「同时打到数据库的请求」从 N 个降成 1 个。锁带 10 秒过期时间防止死锁，重建完成后 finally 里释放。"

### 易被追问的点
- 为什么锁要设过期时间（防止进程崩溃后锁永不释放）；
- 逻辑过期 vs 互斥锁的取舍（逻辑过期不阻塞但可能短暂返回旧数据）；
- double check 的作用（拿到锁后缓存可能已被别的线程写好，避免重复查库）。

## 四、幂等性（用户操作防重复）

### 概念
同一个请求（或用户短时间内连点多次）执行多次，结果与执行一次完全一致，不会产生副作用。下单、支付这类「写操作」必须幂等。

### 本项目落地情况（本次已实现）
- 采用 **Token 防重复提交** 方案：
  1. 新增 `GET /user/order/submitToken` 接口：下单前先获取一次性 token，存 Redis（key = `submit_token_{userId}`，10 分钟过期）；
  2. 下单 `submit` 接口开头，用 `redisTemplate.delete(tokenKey)` 原子删除 token：
     - 删除成功 → 说明是首次有效提交，继续下单；
     - 删除失败 / token 为空 → 说明 token 已用过或过期，直接返回「请勿重复提交订单」。

### 面试答题思路
> "下单要防重复提交。我让用户先调一个接口拿一次性 token 存 Redis，提交订单时用 Redis 的 delete 原子删除这个 token——删得掉说明是第一次提交，删不掉就拒绝。delete 是原子操作，天然保证了并发下只有一个请求能通过校验。"

### 易被追问的点
- 为什么用 Redis 的 delete 而不是「先 get 再判断再删」（get+判断+删不是原子，会有竞态）；
- 幂等的其他方案：数据库唯一约束、乐观锁 version、状态机（订单状态流转天然幂等）、分布式锁；
- 支付回调（`PayNotifyController`）为什么也要幂等：微信可能重复回调，要按订单号判重。

## 五、缓存容量问题（内存膨胀 / 淘汰策略）

### 概念
Redis 是内存数据库，如果缓存**不设过期时间**，数据会永久驻留、内存只增不减，最终 OOM。所以要关注：
- **过期时间（TTL）**：每个 key 设置生存时间，到期自动删除；
- **淘汰策略（maxmemory-policy）**：内存达到上限后按策略淘汰 key。

### 本项目落地情况（本次已实现）
- **菜品缓存**（`user/DishController`）：写入时改为 `set(key, list, ttl, TimeUnit.MINUTES)`，设置「30 分钟基础 + 0~10 分钟随机」的过期时间；
- **套餐缓存**（Spring Cache 注解）：新增 `CacheConfiguration` 配置类，统一为 `setmealCache` 配置 `entryTtl`，并改用 **JSON 序列化**（`GenericJackson2JsonRedisSerializer`）替代默认 JDK 序列化。

### 面试答题思路
> "原来的菜品和套餐缓存都没设过期时间，长期运行内存会只增不减。我给菜品缓存加上了 30 分钟左右的随机过期时间，套餐缓存通过 RedisCacheManager 统一配了 TTL。随机值一方面控制内存容量，另一方面避免大量 key 同时过期造成雪崩。"

### 易被追问的点
- Redis 淘汰策略有哪些：`noeviction` / `allkeys-lru` / `volatile-lru` / `allkeys-lfu` / `volatile-ttl` 等，各适用什么场景；
- 过期删除机制：惰性删除 + 定期删除，而不是到期立刻删；
- JDK 序列化 vs JSON 序列化的区别：JDK 序列化要求对象实现 `Serializable`、不可读、体积大；JSON 可读、跨语言，但需要处理类型信息（`GenericJackson2JsonRedisSerializer` 会带上 `@class` 类型字段）。

## 六、缓存与数据库一致性

### 概念
缓存和数据库是两份数据，更新数据库后如何保证缓存不返回旧数据（脏数据），是缓存系统最核心的难题之一。

### 主流方案：Cache-Aside（旁路缓存）模式
这是本项目用的模式，也是最常见的：

- **读**：先查缓存，命中直接返回；未命中查库，写回缓存；
- **写**：**先更新数据库，再删除缓存**（而不是更新缓存）。

**为什么删缓存而不是更新缓存？**
- 删缓存简单、幂等；更新缓存容易在并发下出现「更新顺序错乱」导致缓存和 DB 不一致；
- 删缓存后，下次读会懒加载重建，天然走最新数据。

### 本项目落地情况
- **写路径**：admin 端更新菜品/套餐时，都是「先 `dishService.updateWithFlavor()` 更新 DB，再 `clearCache` / `@CacheEvict` 删缓存」，顺序正确；
- **兜底**：本次新增的 **TTL 过期时间**是最终一致性的兜底——即使某次删除漏了，缓存也会在过期后自动失效、重新加载最新数据。

### 面试答题思路
> "我用的 Cache-Aside 模式：读时先查缓存再查库，写时先更新数据库再删缓存。删缓存而不是更新缓存，能避免并发更新顺序错乱。另外我给缓存都加了过期时间，作为兜底，就算极端情况下缓存和库短暂不一致，也会在过期后自愈。"

### 易被追问的点（进阶）
- **先删缓存再更新库** vs **先更新库再删缓存** 的优劣：先删缓存 + 更新库，中间有请求读到旧库数据又写回旧缓存 → 脏数据；先更新库 + 删缓存，中间窗口读旧缓存的概率更小，但仍不是绝对一致；
- **延迟双删**：更新库后删缓存，延迟几百毫秒再删一次，解决「删缓存后、另一个线程又读旧库数据写回缓存」的竞态；
- **最终一致性 vs 强一致性**：缓存方案本质是最终一致，要强一致得靠分布式事务/消息队列（如订阅 binlog 同步缓存）；
- **Canal + MQ**：监听 binlog 变更，异步刷新缓存，是大厂常见的一致性方案。

## 七、一页速记表

| 概念 | 一句话 | 本项目落地 |
|------|--------|-----------|
| 多线程 | 抢占/睡眠/锁竞争，共享资源要同步 | ThreadLocal 隔离 + 击穿防护的自旋 sleep |
| 超卖 | 检查+扣减非原子导致卖超 | 无库存，不涉及；但要会讲防超卖方案 |
| 缓存穿透 | 查不存在的 key 打穿 DB | 未处理，可用空值缓存/布隆过滤器 |
| 缓存击穿 | 热点 key 过期瞬间打爆 DB | **已实现**：setIfAbsent 互斥锁 + 自旋 |
| 缓存雪崩 | 大量 key 同时过期 | **已实现**：过期时间加随机值（30+随机分钟） |
| 缓存容量 | 内存只增不减会 OOM | **已实现**：菜品/套餐都设 TTL |
| 缓存一致性 | 缓存与 DB 数据不一致 | Cache-Aside 先更库再删缓存 + TTL 兜底 |
| 幂等性 | 重复执行结果一致 | **已实现**：下单 Token 原子删除 |
