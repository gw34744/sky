## 二、索引原理（B+ 树）

### 为什么用 B+ 树而不是别的结构？
- **二叉树/红黑树**：高度随数据量增长，磁盘 IO 次数多；
- **哈希表**：等值查询快，但**不支持范围查询**和排序（`>`, `<`, `between`, `order by`）；
- **B 树**：每个节点既存 key 又存数据，非叶子节点也能存数据，导致每层能装的 key 变少、树变高；
- **B+ 树**：
  1. **非叶子节点只存 key 不存数据** → 每个节点能存更多 key → 树更矮 → 磁盘 IO 更少（InnoDB 一般 3~4 层）；
  2. **叶子节点用链表串联** → 天然支持范围查询和有序遍历；
  3. 数据全部存在叶子节点，查询性能稳定。

### InnoDB 的聚簇索引 vs 二级索引
- **聚簇索引（主键索引）**：叶子节点直接存**整行数据**；
- **二级索引（普通索引）**：叶子节点存的是**主键值**，查到后还要「回表」去聚簇索引查整行；
- **回表**：二级索引找到主键 → 再回主键索引查数据，多一次 IO。这就是「覆盖索引」要解决的。

### 面试答题思路
> "InnoDB 用 B+ 树做索引。非叶子节点只存 key、叶子节点用链表串起来，所以树矮、IO 少，且支持范围查询。主键索引的叶子存整行数据，二级索引的叶子存主键，查到后还要回表。"

## 三、最左前缀原则

### 概念
联合索引 `(a, b, c)` 相当于建了 `(a)`、`(a, b)`、`(a, b, c)` 三个索引，但**不包含** `(b)`、`(b, c)`、`(c)`。所以查询条件必须**以联合索引最左边的列开头**才能命中。

### 面试答题思路
> "联合索引有最左前缀原则：比如 (status, order_time) 这个索引，where status = ? 能命中，where status = ? and order_time < ? 也能命中，但只 where order_time < ? 就命不中。所以建联合索引时，把区分度高、常用作等值条件的字段放最左边。"

---

## 四、覆盖索引

### 概念
查询的列**全部**在索引里，不需要回表，直接从索引拿到结果，就叫「覆盖索引」。

### 例子
```sql
-- 如果 order_detail 建了 (order_id, name) 联合索引，
-- 这个查询只查 name，可以直接从索引拿，不用回表：
SELECT name FROM order_detail WHERE order_id = 1;
```

### 面试答题思路
> "覆盖索引就是让查询的字段都在索引里，避免回表。常见做法是用联合索引，把常用的查询列都放进索引，或者用 explain 看 Extra 列有没有 Using index。"

## 五、查询优化（Explain 分析）

### 核心：EXPLAIN 看什么
| 字段 | 关注点 |
|---|---|
| type | 从好到坏：system > const > eq_ref > ref > range > index > **ALL（全表扫描，要避免）** |
| key | 实际用到的索引，NULL 说明没用索引 |
| rows | 扫描行数，越少越好 |
| Extra | `Using index`（覆盖索引，好）/ `Using filesort`（排序没走索引）/ `Using temporary`（临时表，差） |

### 常见优化点
1. **避免 `SELECT *`**：只查需要的列，利于覆盖索引、减少传输；
2. **避免在索引列上做函数/运算**：`where year(order_time) = 2023` 会导致索引失效，应写成 `where order_time between '2023-01-01' and '2023-12-31'`；
3. **前导模糊查询不走索引**：`like '%abc'` 失效，`like 'abc%'` 可用；
4. **隐式类型转换**：字符串字段传数字会导致索引失效；
5. **大表分页优化**：`limit 100000, 10` 深分页慢，可用「延迟关联」或记录上次 id 的游标方式。

### 本项目实例
- 订单分页 `order by order_time desc`，若 `order_time` 无索引会 Using filesort → 可考虑给 order_time 建索引；
- `getSalesTop10` 用 `order_detail od, orders o where od.order_id = o.id` 联表统计，`od.order_id` 和 `o.id` 都需要索引（本次已补 order_id）。

## 六、分表分库

### 概念（知识储备，本项目未落地）
- **为什么要分**：单表数据量过大（如订单表上千万、上亿），单库写入/查询成为瓶颈；
- **水平分表（分片）**：按某个字段（如 user_id）把数据拆分到多个表/库，如 `order_0`、`order_1`……；
- **垂直分表**：把大字段、不常用字段拆出去，减少单行体积；
- **垂直分库**：按业务拆分（用户库、订单库、商品库）。

### 分片键（sharding key）的选择
- 选**查询最频繁、区分度高**的字段，如订单表的 `user_id`；
- 要避免「跨分片查询」（比如按 order_id 查，但分片键是 user_id，就得广播到所有分片）。

### 面试答题思路
> "分表是知识储备，我这个教学项目数据量小、没做。但我知道：水平分表按分片键把数据打散到多张表，分片键一般选高频查询且区分度高的字段；代价是跨分片查询、分布式事务、全局唯一 id（雪花算法）变复杂。"

### 本项目可扩展点（如果真要做）
- 订单表 `orders` 最可能先到瓶颈，可按 `user_id` 或 `order_time`（按月）分表；
- 全局 id：目前用 `AUTO_INCREMENT`，分表后要换成雪花算法保证全局唯一。

## 七、存储引擎（InnoDB vs MyISAM）

| 维度 | InnoDB（本项目用的） | MyISAM |
|---|---|---|
| 事务 | 支持 | 不支持 |
| 行锁/表锁 | 行锁（并发好） | 表锁 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 支持（redo log） | 较差 |
| 索引结构 | B+ 树，聚簇索引 | B+ 树，非聚簇 |

### 面试答题思路
> "项目用的 InnoDB，因为需要事务（下单、支付）和行级锁（并发）。InnoDB 是聚簇索引，主键和数据在一起，二级索引要回表；MyISAM 不支持事务、是表锁，适合只读场景。"
