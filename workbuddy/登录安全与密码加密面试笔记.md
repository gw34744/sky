# 登录安全 & 密码加密 面试笔记

> 配合「苍穹外卖」项目，讲清楚密码加密、加盐、char[] 存储、HTTPS 全程加密这些登录安全高频考点。

---

## 一、项目现状与改造（真实落地）

### 改造前的问题
- 密码用 **MD5（无盐）**：MD5 是快速哈希，可被彩虹表、暴力破解（GPU 每秒几十亿次）；
- **无盐**：相同密码的 MD5 完全一样，撞库/彩虹表一击即中；
- 用 `String` 存密码：String 不可变，密码明文会滞留内存堆、无法主动清零。

### 本次改造
1. **引入 BCrypt**（`spring-security-crypto`，BCryptPasswordEncoder）替换 MD5；
2. **登录校验**：`passwordEncoder.matches(password, employee.getPassword())`；
3. **新增员工**：`passwordEncoder.encode("123456")` 加密后入库；
4. **数据库**：`employee.password` 字段从 `varchar(64)` 扩到 `varchar(100)`，admin 密码重置为 BCrypt 格式。

### 面试答题思路
> "我原来的密码是 MD5 无盐存储的，不安全。我改成了 BCrypt：它每次加密都自动生成随机盐，相同密码每次结果都不同，天然抗彩虹表；而且是慢哈希，可以通过 strength 参数调节计算成本，加大暴力破解难度。"

---

## 二、为什么 BCrypt 比 MD5 好

| 维度 | MD5 | BCrypt |
|---|---|---|
| 加盐 | 默认无盐，需手动加 | **自动随机盐** |
| 速度 | 快（几十亿次/秒） | **慢哈希**，可调成本因子 |
| 抗彩虹表 | 弱（无盐时一击即中） | 强（盐不同，无法预计算） |
| 抗暴力破解 | 弱 | 强（慢哈希拖慢尝试速度） |
| 输出 | 32 位十六进制 | 60 字符（含版本+强度+盐+哈希） |

### 核心原理
BCrypt 的哈希串 `$2a$10$...` 分四段：
- `$2a$`：算法版本；
- `10`：成本因子（cost factor），2^10 = 1024 次迭代，越大越慢越安全；
- 中间 22 位：随机盐；
- 最后 31 位：哈希结果。

**验证时**，`matches` 会从存储的哈希里提取盐和成本因子，重新计算并比对——所以不需要单独存盐。

### 面试答题思路
> "BCrypt 的盐是嵌在哈希结果里的，验证时自动提取，不需要单独的盐字段。成本因子 10 表示 2 的 10 次方次迭代，可以调大来应对算力增长。"

## 三、加盐（Salt）

### 概念
给每个密码拼接一个**随机**的字符串再哈希，这样即使两个用户密码相同，哈希结果也不同，攻击者无法用预计算的彩虹表一次性破解所有密码。

### 关键点
- **盐要随机、且每个用户不同**：固定盐或全局盐等于没加；
- **盐不用保密**（可以明文存），它的作用是让彩虹表失效，而不是增加未知性；
- BCrypt / Argon2 / scrypt 这类算法**内置了盐处理**，比自己手动"MD5(password + salt)"更安全。

### 面试答题思路
> "加盐就是给每个密码拼一个随机字符串再哈希，核心是让相同密码产生不同结果、破解彩虹表。盐可以明文存，关键是每个用户随机。我用的 BCrypt 内部就自动加盐了，比自己拼字符串更规范。"

## 四、char[] 存储密码（vs String）

### 为什么用 char[] 而不是 String
- **String 不可变**：一旦创建，密码明文在内存堆里无法被修改或擦除，直到 GC 回收（GC 时机不可控）；
- **char[] 可变**：用完可以 `Arrays.fill(password, '\0')` 主动清零，缩短密码在内存中的存活时间；
- 内存 dump 时，String 会以明文形式被看到，char[] 清零后则不会。

### 本项目现状（诚实版）
- 当前代码用的是 `String` 存密码（教学项目常见做法）；
- char[] 是「知识储备」，面试能讲清楚即可，实际项目里可结合 `javax.security.auth` 的 `PasswordCallback` 或自定义 char[] 处理。

### 面试答题思路
> "密码应该用 char[] 存而不是 String，因为 String 不可变，密码会滞留在内存堆直到 GC；char[] 可以主动 Arrays.fill 清零，缩短明文存活时间。项目里我目前用 String，但我了解这个最佳实践，知道为什么 char[] 更安全。"

## 五、全程加密（HTTPS / TLS）

### 概念
- **HTTPS = HTTP + TLS/SSL**：在传输层加密，防止密码等敏感信息在网络上被明文窃听（中间人攻击）；
- 只做**传输加密**还不够，还要**存储加密**（BCrypt），两者是不同环节。

### 本项目落地情况
- 代码层面没有直接体现 HTTPS（依赖 Nginx/网关配置 TLS 证书）；
- 项目里有 `nginx-1.20.2` 目录，生产部署时应在 Nginx 配置 443 端口 + SSL 证书。

### 面试答题思路
> "登录安全分两层：传输层用 HTTPS/TLS 加密，防止中间人窃听；存储层用 BCrypt 加密，防止数据库泄露后被直接破解。我这个项目传输层依赖部署时配 Nginx 的 SSL 证书，存储层我改成了 BCrypt。"

### 易被追问的点
- HTTPS 握手流程（TCP → TLS 握手 → 对称加密通信）；
- 对称加密 vs 非对称加密：TLS 握手用非对称交换密钥，之后用对称加密（性能好）；
- 为什么前端也要考虑加密：即使 HTTPS，前端密码在浏览器内存、日志里也可能泄露，但**前端加密不能替代后端加密**（前端加密密钥可被扒）。

## 六、其他登录安全点（加分项）

1. **登录失败限制**：连续失败 N 次锁定账号（防暴力破解）——本项目有 `status` 锁定字段，但未做自动锁定逻辑；
2. **验证码**：防止机器人暴力破解；
3. **Token 安全**：JWT 要设过期时间（本项目 admin-ttl 2 小时）、密钥不硬编码（本项目 `itcast` 是硬编码，生产要改）；
4. **防撞库**：不要返回"用户名不存在"和"密码错误"区分太细（本项目分开了，严格说可优化为统一"用户名或密码错误"）；
5. **日志脱敏**：不要把密码写进日志（`log.info` 不要打印 DTO 里的 password）。
