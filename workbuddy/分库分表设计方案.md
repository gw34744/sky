# 苍穹外卖分库分表设计方案

> 目标：为苍穹外卖的订单体系设计一套可落地的分库分表方案，补齐「数据库优化」的深度，覆盖面试高频考点。
> 关联：此前已完成「数据库索引优化」（单表内优化），本文档解决「单表大到扛不住」时的**分库分表**演进。

---

## 一、为什么需要分库分表（先讲清楚动机）

单表（索引优化后）能扛的极限大约在 **千万级**，超过后会遇到：

1. **数据量过大**：`orders` 表随时间无限增长，几千万行后 B+ 树层级变深，单条查询/写入都变慢；
2. **写入瓶颈**：单表写入集中在同一棵 B+ 树，并发写会争抢锁；
3. **数据库单点**：所有请求打到同一台 MySQL，连接数、CPU、磁盘 I/O 都会到顶；
4. **备份/DDL 困难**：大表 `ALTER` 加字段可能锁表数小时，备份恢复慢。

**分库分表的本质**：把「一个大表/一个大库」拆成「多个小表/多个小库」，让数据分散到多台机器/多个表，从而横向扩展。

---

## 二、分库分表的核心概念（面试必背）

| 概念 | 含义 |
|------|------|
| **垂直分库** | 按业务模块把不同表放到不同库（订单库、用户库、商品库），解耦不同业务 |
| **垂直分表** | 把一张宽表按字段拆成多张表（大字段拆分、冷热分离），减少单行大小 |
| **水平分库** | 把同一张表的数据按规则分散到多个库 |
| **水平分表** | 把同一张表的数据按规则分散到同一库的多个表 |
| **分片键（Sharding Key）** | 决定数据落到哪个分片的那一列，如 `user_id` |
| **分片算法** | 取模、范围、哈希、一致性哈希等 |

> 日常说的「分库分表」通常指 **水平分库 + 水平分表**，本文重点也是这个。

## 三、苍穹外卖的分库分表方案

### 3.1 垂直分库（按业务模块拆库）

| 库 | 表 | 说明 |
|----|----|------|
| `sky_order`（订单库） | orders、order_detail | 订单核心，读写最频繁、增长最快 |
| `sky_user`（用户库） | user、address_book、shopping_cart | 用户与地址、购物车 |
| `sky_goods`（商品库） | dish、dish_flavor、setmeal、setmeal_dish、category | 商品/分类，读多写少 |
| `sky_system`（系统库） | employee | 后台员工 |

**好处**：
- 订单库高负载不会拖垮商品/用户库；
- 不同库可独立扩容、独立备份、独立部署。

### 3.2 水平分表（订单表拆分，核心）

订单表和订单明细表是**随时间无限增长**的表，是水平分表的主战场。

**分片键选择：`user_id`**（而非订单号或时间），理由：

| 候选分片键 | 优点 | 缺点 | 结论 |
|-----------|------|------|------|
| `user_id` | 用户查「我的订单」是最高频查询，能精确路由到单个分片 | 管理端按状态/时间全量统计要跨所有分片 | ✅ 首选 |
| `order_time`（时间） | 天然适合冷热数据归档 | 用户查自己订单要跨所有时间分片 | 适合归档场景 |
| `number`（订单号） | 唯一 | 按用户查订单无法路由 | ❌ 不适合 |

> 外卖场景最核心的查询是「用户查自己的历史订单」，所以用 `user_id` 取模分片，能让最高频查询只命中一个分片。

**分表数量：16 张**（orders_0 ~ orders_15），分片算法：`user_id % 16`。

**配套的 order_detail 也按同样规则分 16 张**，且用**同一个 `order_id` 路由到同一分片**（保证订单和明细在同一分片，避免跨分片 join）。

## 四、关键改造点：主键必须改雪花算法

### 为什么自增主键不能用

黑马原版的 `orders.id` 是 `AUTO_INCREMENT`。分表后，**每张表都从 1 开始自增**，会导致 `orders_0`、`orders_1` 里都有 `id=1` 的订单——**主键全局冲突**。

### 解决方案：雪花算法（Snowflake）

项目里已有 `SnowflakeIdUtil`（之前订单号已经改用它）。分库分表时，**订单主键 `id` 和订单号 `number` 都应由雪花算法生成全局唯一 ID**。

雪花算法 64 位结构：

```
0 | 41位时间戳 | 10位机器ID | 12位序列号
```

- **全局唯一**：不同机器、不同时间生成的 ID 不重复；
- **趋势递增**：时间戳在高位，ID 随时间递增，利于 B+ 树写入；
- **不依赖数据库自增**：分库分表后依然唯一。

> 面试追问「雪花算法有什么问题」：① 依赖机器时钟，时钟回拨会重复（项目 `SnowflakeIdUtil` 已做时钟回拨处理）；② 10 位机器 ID 最多 1024 台机器。

## 五、分片路由方案

### 5.1 客户端路由（推荐学习用：ShardingSphere-JDBC）

在应用层引入 **Apache ShardingSphere-JDBC**，通过配置分片规则，透明地完成分库分表：

```yaml
# sharding-sphere 配置示意
spring:
  shardingsphere:
    rules:
      sharding:
        tables:
          orders:
            actual-data-nodes: sky_order.orders_$->{0..15}
            table-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: orders-inline
        sharding-algorithms:
          orders-inline:
            type: INLINE
            props:
              algorithm-expression: orders_$->{user_id % 16}
```

**好处**：业务代码几乎无感知，`SELECT * FROM orders WHERE user_id = ?` 自动路由到对应分片。

### 5.2 代理层路由（ShardingSphere-Proxy / MyCat）

用独立代理层，应用连代理，代理负责分片路由。好处是**对应用完全透明**，但多一层网络开销和运维成本。

### 5.3 项目建议

- **学习阶段**：ShardingSphere-JDBC（代码可理解、可 debug，面试能讲清楚原理）；
- **生产阶段**：视团队情况选 JDBC 或 Proxy。

## 六、分库分表带来的问题与解决（面试重点！）

分库分表不是免费的，引入后要解决一系列问题：

| 问题 | 说明 | 解决方案 |
|------|------|---------|
| **全局唯一 ID** | 自增主键冲突 | 雪花算法 / 号段模式 / Redis 自增 |
| **跨分片查询** | 管理端按状态/时间统计要跨所有分片 | 汇总查询 + 归并排序，或用 ES 做宽表 |
| **跨分片事务** | 订单和明细若分到不同分片，无法用单库事务 | 分片键设计保证相关数据同分片；分布式事务（Seata/XA/TCC）兜底 |
| **分页/排序** | 跨分片分页要「各分片取 topN 再归并」 | ShardingSphere 自动归并；深分页改游标 |
| **join 限制** | 跨分片无法 join | 冗余字段、拆成多次查询、宽表 |
| **扩容（数据迁移）** | 从 16 张扩到 32 张要迁移数据 | 一致性哈希、双写过渡、停机/在线迁移 |
| **全局表** | 有些表每个分片都要（如字典表） | 广播表（每个库一份） |

### 重点讲透：为什么「订单 + 明细」要放同一分片

`orders` 和 `order_detail` 是 1:N 关系，查询订单详情要 join。如果两张表按不同规则分片，同一个订单的明细可能散在不同分片，**无法用单库事务保证一致性**。

**设计原则**：让**关联数据落在同一分片**。这里用 `order_id`（即订单主键）作为 order_detail 的分片键，与 orders 保持一致，这样订单和它的明细一定在同一分片，事务和 join 都能在单库内完成。

---

## 七、扩容策略（从 16 → 32 表）

当单分片数据量再次逼近瓶颈时扩容：

1. **一致性哈希**：避免取模扩容时大量数据重分布；
2. **双写过渡**：新老分片同时写，读逐步切新，稳定后停老；
3. **停机迁移 vs 在线迁移**：数据量大用在线迁移（binlog 同步 + 灰度）。

> 面试高频：「取模分片扩容为什么痛苦？」答：取模算法扩容（16→32）会导致几乎所有数据要重新计算分片、大量搬迁；一致性哈希能减少迁移量。

## 八、与项目现有改造的衔接

| 已有改造 | 与分库分表的关系 |
|---------|----------------|
| `SnowflakeIdUtil` 雪花算法 | ✅ 分表后主键/订单号直接复用，无需自增 |
| 订单号 `number` 已改雪花 | ✅ 全局唯一，分表不冲突 |
| 索引优化（idx_orders_user_id 等） | ✅ 每个分表内仍需这些索引，分表后单表变小，索引效率更高 |
| 支付回调幂等（getByNumber） | ⚠️ 按 `number` 查订单**无法路由**到分片，需额外处理（见下） |

### 特别注意：`getByNumber` 的路由问题

支付回调、来单提醒都是**按订单号 `number` 查订单**，但分片键是 `user_id`，导致：

- 按 `number` 查询时，**不知道 user_id，无法路由到具体分片**，只能广播所有分片查询。

**解决方案（三选一）**：
1. **订单号编码 user_id**：把 user_id 编码进雪花生成的订单号，查询时从 number 反解出 user_id 再路由（推荐）；
2. **建立 number → (user_id, 分片) 的映射表/索引**（如 Redis 缓存映射）；
3. **广播查询**：所有分片都查一遍（简单但性能差）。

> 这是分库分表设计里「非分片键查询」的经典难题，面试讲出来很加分。

## 九、高频面试问答

**Q1：什么时候该分库分表？**
A：单表数据量到千万级、或单库 QPS/连接数到瓶颈。不能一上来就分（复杂度高），先做索引优化、读写分离、缓存，都不够了再分。

**Q2：分片键怎么选？**
A：选「最核心、最高频的查询字段」，让大部分查询能精确路由到单个分片，避免广播。本项目选 `user_id`。

**Q3：分片键选错了怎么办？**
A：很难改（要数据迁移）。所以设计时就要想清楚核心查询场景。如果确实错了，只能双写迁移 + 灰度切换。

**Q4：ShardingSphere 的原理？**
A：JDBC 版是在 JDBC 层拦截 SQL，根据分片规则改写 SQL 并路由到对应数据源，再归并结果。应用只配规则，业务代码基本无感。

**Q5：分库分表和读写分离的区别？**
A：读写分离是「一主多从，读走从库」，解决读压力；分库分表是「数据分散」，解决单表/单库容量和写压力。两者常组合使用。

**Q6：分布式 ID 有哪些方案？**
A：① 雪花算法（趋势递增、全局唯一）；② 号段模式（如美团 Leaf，每次取一段）；③ Redis INCR（简单但有单点）；④ UUID（唯一但无序，不利于 B+ 树）。

## 十、总结：三层演进路径

```
单表(索引优化) ──> 读写分离(一主多从) ──> 分库分表(水平拆分)
   已做 ✅            可做(下一步)          本文档设计
```

面试叙事：**先做单表索引优化 → 数据量增长后引入读写分离 → 再大就分库分表**，层层递进，体现工程化思维。
