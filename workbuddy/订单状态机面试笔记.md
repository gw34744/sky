# 订单状态机 面试笔记

> 对应简历技术点：**订单状态机建模、状态流转合法性校验**。
> 本文档配合代码落地：`OrderStatus`（枚举状态机）、`OrderServiceImpl`（4 个状态转换方法改用状态机校验）、
> `OrderStatusTest`（7 个用例验证状态机规则）。

---

## 一、问题背景：原来怎么做的，有什么缺陷

订单有 6 个状态（待付款/待接单/已接单/派送中/已完成/已取消），原项目在 `OrderServiceImpl` 的
`confirm`/`rejection`/`delivery`/`complete` 等方法里，**每个方法手写 if 判断当前状态**：

```java
// 原来：每个方法各自写"状态必须等于XX才能执行"
if (orderDB == null || !orderDB.getStatus().equals(Orders.TO_BE_CONFIRMED)) {
    throw new OrderBusinessException(MessageConstant.ORDER_STATUS_ERROR);
}
```

**缺陷：**

1. **规则散落**：合法流转关系分散在 4+ 个方法里，看不出「订单全生命周期」的完整状态图；
2. **易遗漏**：新增一个状态或调整流转规则，要改多处，容易漏改导致逻辑不一致；
3. **难测试**：没有集中的规则可单独验证，只能靠业务方法的集成测试间接覆盖；
4. **可读性差**：状态码是魔法数字 `1/2/3/4/5/6`，语义靠注释而非代码本身表达。

---

## 二、状态机是什么（核心概念）

**状态机（State Machine）= 状态 + 转移**。一个对象从「当前状态」出发，只有在「合法转移」被定义时才能进入「目标状态」。

```
状态集合：{待付款, 待接单, 已接单, 派送中, 已完成, 已取消}
转移规则（合法流转表）：
  待付款 ──支付──▶ 待接单
  待付款 ──取消──▶ 已取消
  待接单 ──接单──▶ 已接单
  待接单 ──拒单──▶ 已取消
  已接单 ──派送──▶ 派送中
  已接单 ──取消──▶ 已取消
  派送中 ──完成──▶ 已完成
  已完成 ──（终态，无出口）
  已取消 ──（终态，无出口）
```

**状态机的价值**：把「什么状态能变成什么状态」这个**业务规则**从「散落的 if」中提取出来，**集中建模、集中校验、集中测试**。

## 三、本项目的实现（枚举状态机）

### 1. OrderStatus 枚举（sky-common/enumeration）

```java
public enum OrderStatus {
    PENDING_PAYMENT(1), TO_BE_CONFIRMED(2), CONFIRMED(3),
    DELIVERY_IN_PROGRESS(4), COMPLETED(5), CANCELLED(6);

    // 状态机核心：合法流转表
    private static final Map<OrderStatus, Set<OrderStatus>> TRANSITIONS = buildTransitions();

    private static Map<OrderStatus, Set<OrderStatus>> buildTransitions() {
        map.put(PENDING_PAYMENT, setOf(TO_BE_CONFIRMED, CANCELLED));
        map.put(TO_BE_CONFIRMED, setOf(CONFIRMED, CANCELLED));
        map.put(CONFIRMED, setOf(DELIVERY_IN_PROGRESS, CANCELLED));
        map.put(DELIVERY_IN_PROGRESS, setOf(COMPLETED));
        map.put(COMPLETED, setOf());   // 终态
        map.put(CANCELLED, setOf());   // 终态
        ...
    }

    public static boolean canTransition(OrderStatus current, OrderStatus target) { ... }
    public static void checkTransition(OrderStatus current, OrderStatus target) {
        if (!canTransition(current, target)) throw new OrderBusinessException(ORDER_STATUS_ERROR);
    }
}
```

**设计要点：**
- **状态码自持**：状态码 1~6 用字面量写在枚举里，与实体 `Orders` 常量保持一致，但**不反向依赖实体类**（枚举在 sky-common，实体在 sky-pojo，避免模块耦合）；
- **EnumMap + Set**：合法流转表用 `EnumMap<状态, Set<目标状态>>` 表达，O(1) 查询；
- **终态无出口**：`COMPLETED`/`CANCELLED` 的合法目标为空集，任何流转都会被拒绝。

### 2. 业务方法改用状态机校验

```java
// confirm：待接单 → 已接单
OrderStatus.checkTransition(OrderStatus.of(orderDB.getStatus()), OrderStatus.CONFIRMED);

// delivery：已接单 → 派送中
OrderStatus.checkTransition(OrderStatus.of(orderDB.getStatus()), OrderStatus.DELIVERY_IN_PROGRESS);

// complete：派送中 → 已完成
OrderStatus.checkTransition(OrderStatus.of(orderDB.getStatus()), OrderStatus.COMPLETED);

// rejection：待接单 → 已取消
OrderStatus.checkTransition(OrderStatus.of(orderDB.getStatus()), OrderStatus.CANCELLED);
```

改造后：每个方法只关心「我要把订单转到哪个状态」，**合法性由状态机统一保证**，不需要知道「从哪个状态能转过来」。

### 3. 独立测试（OrderStatusTest，7 用例）

状态机「集中定义规则」的最大好处是**可以独立、精确地测试规则本身**：

- 主流程合法流转（4 步）
- 取消分支（3 个状态都可取消）
- 终态无出口
- 非法跳转被拒（已接单不能直接完成、派送中不能回退）
- checkTransition 非法抛异常 / 合法不抛
- 状态码与枚举互转

## 四、面试高频问答

**Q1：什么是状态机？你的项目里状态机怎么落地？**
状态机是「状态 + 转移规则」的建模方式。我用枚举 `OrderStatus` + 一张 `EnumMap<状态, Set<目标状态>>` 合法流转表来落地，业务方法统一调 `checkTransition(current, target)` 校验，非法流转抛业务异常。

**Q2：为什么用枚举实现状态机，而不是 if-else 或 switch？**
枚举实现状态机，把流转规则集中在一处，可读、可维护、可单独测试；if-else 会把规则散落到各处，新增状态/调整规则要改多处易漏。且枚举天然单例、类型安全，不会传错状态码。

**Q3：状态机解决了原来什么问题？**
原来每个状态转换方法各自手写 `if (status != 期望值)`，规则散落、魔法数字、难测试。状态机把「合法流转关系」集中建模，业务方法只声明「目标状态」，合法性统一校验。

**Q4：终态怎么处理？**
终态（已完成、已取消）的合法目标集合为空集，`canTransition` 一定返回 false，任何从终态出发的流转都会被拒绝，防止订单被错误地「复活」或二次流转。

**Q5：订单状态和支付状态是什么关系？**
两个独立维度：订单状态（待付款→…→已完成）描述业务流转；支付状态（未支付/已支付/退款）描述支付结果。二者正交，比如「待接单」的订单支付状态一定是「已支付」。项目里 `Orders` 同时维护 `status` 和 `payStatus` 两个字段。

**Q6：状态机可以用框架实现吗？**
可以，业界有 Spring StateMachine（重量级，适合复杂多状态、带守卫/动作的场景）。但对订单这种「线性主流程 + 少量分支」的简单状态机，手写枚举状态机更轻量、可读性更好，不必引入重框架。

**Q7：状态流转的并发问题怎么处理？**
两个并发请求同时把订单从「待接单」转到「已接单」，状态机校验会都通过，导致重复接单。解决方案：① 数据库乐观锁（`update ... where status = 旧值`，影响行数为 0 说明已被并发修改）；② 分布式锁；③ 条件更新（CAS）。本项目状态机解决「合法性」问题，并发安全需配合乐观锁/CAS 进一步加固。

## 六、可扩展方向（面试加分）

- **乐观锁/CAS 加固并发**：`update orders set status = 新值 where id = ? and status = 旧值`，用影响行数判断是否被并发修改；
- **状态变更历史表**：记录每次状态流转的「谁、何时、从哪到哪」，支持审计与回溯；
- **守卫条件（Guard）**：状态转移附加上下文条件（如「只有支付状态=已支付才能接单」）；
- **Spring StateMachine**：若状态复杂到需要「层级状态、并发子状态、历史状态」再引入框架。
