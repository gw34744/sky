# 限流与熔断降级面试笔记（Resilience4j）

> 对应改动：`sky-server/pom.xml` 引入 resilience4j、`application.yml` 配置限流/熔断、
> `OrderController` 加 @RateLimiter、`OrderServiceImpl` 加 @CircuitBreaker
> 主题：应用层限流熔断，与 Nginx 网关限流形成「网关+应用」双层防护

---

## 一、为什么需要限流和熔断

### 1. 限流（Rate Limiting）
控制「单位时间内」进入系统的请求数量，防止流量突增打垮系统。

- **场景**：下单接口被刷单、恶意高频提交、秒杀突发流量；
- **本质**：系统处理能力有上限，超过就要「拒绝」而非「硬扛到崩溃」。

### 2. 熔断（Circuit Breaking）
当下游服务/数据库连续失败时，**暂时切断对它的调用**，快速失败，避免「雪崩」。

- **场景**：数据库挂掉、下游服务超时，调用方不断重试导致资源耗尽；
- **本质**：像电路保险丝，故障时断开，恢复后自动重试（半开状态探测）。

> **核心区别**：限流防「外部流量过大」，熔断防「内部服务故障扩散」。

## 二、为什么选 Resilience4j（而非 Sentinel / Hystrix）

| 方案 | 特点 | 适用 |
|------|------|------|
| **Resilience4j** | 轻量、纯注解、Spring Cloud 官方推荐、无需独立控制台 | 单体/微服务通用，学习成本低 ✅ |
| **Sentinel** | 阿里出品，功能强（流量整形、热点、系统规则），需 Dashboard | 中大型系统、需要可视化监控 |
| **Hystrix** | 已停止维护（进入维护模式） | 不再推荐 |

**本项目选 Resilience4j 的理由**：Spring Boot 2.7.3 直接集成 `resilience4j-spring-boot2`，注解式、无需额外控制台，和单体项目最匹配，且是 Spring Cloud 官方推荐的熔断组件。

## 三、落地实现

### 1. 依赖

```xml
<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-spring-boot2</artifactId>
    <version>1.7.1</version>
</dependency>
```

### 2. 配置（application.yml）

```yaml
resilience4j:
  ratelimiter:
    instances:
      orderSubmit:
        limit-for-period: 5        # 每秒 5 个（防刷单）
        limit-refresh-period: 1s
        timeout-duration: 0        # 超限立即失败
      payment:
        limit-for-period: 10
        limit-refresh-period: 1s
  circuitbreaker:
    instances:
      orderService:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 10    # 最近 10 次调用
        failure-rate-threshold: 50 # 失败率 50% 熔断
        wait-duration-in-open-state: 10s  # 熔断 10 秒后半开
        minimum-number-of-calls: 5 # 至少 5 次调用才统计
```

### 3. 限流注解（Controller 层）

```java
@RateLimiter(name = "orderSubmit", fallbackMethod = "submitFallback")
public Result<OrderSubmitVO> submit(...) { ... }

// fallback：限流时返回友好提示
public Result<OrderSubmitVO> submitFallback(OrdersSubmitDTO dto, String token, Throwable t) {
    return Result.error("下单请求过于频繁，请稍后再试");
}
```

### 4. 熔断注解（Service 层）

```java
@CircuitBreaker(name = "orderService", fallbackMethod = "submitOrderFallback")
public OrderSubmitVO submitOrder(OrdersSubmitDTO dto) { ... }

public OrderSubmitVO submitOrderFallback(OrdersSubmitDTO dto, Throwable t) {
    throw new OrderBusinessException("系统繁忙，下单暂时不可用");
}
```

## 四、熔断器状态机（面试必背）

```
       失败率超阈值
  CLOSED ────────────> OPEN（快速失败，走 fallback）
    ↑                    │
    │                    │ 等待 wait-duration 时间
    │                    ↓
    └──── 成功 ────── HALF_OPEN（放行少量请求探测）
              失败 ────────────> OPEN（继续熔断）
```

- **CLOSED（关闭）**：正常状态，统计调用结果；
- **OPEN（打开）**：失败率超阈值，直接拒绝请求、走 fallback，不调用真实服务；
- **HALF_OPEN（半开）**：等待一段时间后，放行少量请求探测，成功则回 CLOSED，失败则回 OPEN。

## 五、与 Nginx 限流形成「双层防护」

| 层 | 位置 | 作用 | 限流粒度 |
|----|------|------|---------|
| **网关层** | Nginx `limit_req` | 挡在最前面，防大流量进入应用 | 按 IP/接口，粗粒度 |
| **应用层** | Resilience4j | 精确控制关键接口，配合降级 | 按业务接口，细粒度 |

**为什么要双层**：
- Nginx 限流是「第一道闸」，能挡掉大部分恶意流量，但它是**无状态**的，无法感知业务逻辑（比如「下单」比「查询」更该限）；
- Resilience4j 是「第二道闸」，能对**特定业务接口**精细限流 + 熔断降级，还能感知下游故障。

**面试叙事**：网关层粗粒度限流挡住大部分流量，应用层对核心链路（下单、支付）做精细限流 + 熔断降级，两层配合，既防外部刷量，又防内部雪崩。

## 六、高频面试问答

**Q1：限流算法有哪些？**
A：① 固定窗口计数（简单但有临界问题）；② 滑动窗口（更平滑）；③ 漏桶（匀速，固定速率）；④ 令牌桶（允许突发，Resilience4j/Guava 常用）。Resilience4j 的 RateLimiter 默认用「令牌桶」思想。

**Q2：令牌桶 vs 漏桶？**
A：漏桶出水速率恒定，不能突发；令牌桶可以积累令牌，允许一定突发流量。令牌桶更适合电商「平时流量低、瞬时流量高」的场景。

**Q3：熔断和降级有什么区别？**
A：熔断是「保护机制」，下游故障时自动切断调用；降级是「兜底策略」，故障时返回备用逻辑（如返回缓存、默认值、友好提示）。熔断触发后通常配合降级一起用。

**Q4：fallback 方法有什么要求？**
A：签名必须和原方法一致（参数类型、返回类型），末尾可加 `Throwable` 参数接收异常。Resilience4j 通过反射调用 fallback。

**Q5：熔断会不会误伤正常请求？**
A：会通过「半开状态」避免。熔断打开后，等待一段时间会放行少量请求探测，若服务已恢复则关闭熔断恢复正常，避免一直拒绝。

**Q6：限流和熔断什么时候该加？**
A：限流加在「容易被刷/流量突增」的入口（下单、支付、验证码）；熔断加在「依赖外部服务/数据库」的核心链路。不是所有接口都要加，加多了徒增复杂度。
