# 访问通道承载能力评估与高负载优化说明

> 本文档评估苍穹外卖项目访问链路的抗压能力，说明已落地的优化项，以及面向面试的高并发治理要点。

---

## 一、访问通道全链路

```
用户 → Nginx(1.20.2) → Spring Boot(Tomcat) → JWT 拦截器 → Controller → Service → [MySQL(Druid) / Redis(Lettuce)]
```

## 二、优化前的问题盘点

| 环节 | 问题 | 高负载后果 |
|------|------|-----------|
| Tomcat | 全默认，无线程/连接调优 | 默认 maxThreads=200，突发流量线程打满后请求排队 |
| Druid 连接池 | 只声明空 `druid:`，用默认值 | **maxActive=8**，超过 8 个并发请求就阻塞等连接 |
| Redis | 无 Lettuce 连接池 | 无池化，每条命令新建连接，高并发下开销大、可能耗尽 |
| 定时任务 | `@EnableScheduling` 单线程 | 支付超时/派送/心跳任务串行，一个卡住全卡 |
| JWT 拦截器 | `log.info` 打印完整 token | 泄露凭证 + 高负载日志量大 |
| 日志 | mapper 级别 debug | 每条 SQL 都打印，日志 I/O 成为瓶颈 |
| Nginx | 有反向代理但无限流 | 无法抵御突发流量 / 刷单 |

## 三、已落地的优化

### 1. Tomcat 线程池（application.yml）

```yaml
server:
  tomcat:
    threads:
      max: 400          # 最大工作线程
      min-spare: 50     # 最小空闲线程
    max-keep-alive-requests: 200
    connection-timeout: 20000
    accept-count: 200   # 等待队列，超限拒绝而非无限积压
```

### 2. Druid 连接池（最关键的修复）

```yaml
spring:
  datasource:
    druid:
      initial-size: 10
      min-idle: 10
      max-active: 100      # 从默认 8 提到 100
      max-wait: 5000       # 拿连接最多等 5s，超时报错而非无限阻塞
      validation-query: SELECT 1
      test-while-idle: true
      pool-prepared-statements: true
```

### 3. Redis Lettuce 连接池

```yaml
spring:
  redis:
    lettuce:
      pool:
        max-active: 50
        max-idle: 20
        min-idle: 5
        max-wait: 3000ms
```

### 4. 定时任务线程池（新增 SchedulingConfiguration）

```java
@Bean
public ThreadPoolTaskScheduler taskScheduler() {
    ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
    scheduler.setPoolSize(5);        // 5 个线程并行调度
    scheduler.setThreadNamePrefix("sky-schedule-");
    scheduler.setWaitForTasksToCompleteOnShutdown(true);
    return scheduler;
}
```

### 5. JWT 拦截器日志脱敏

- 移除 `log.info("jwt校验:{}", token)`，改为 `log.info("用户 jwt 校验通过，userId={}", userId)`
- 修复 `log.info("当前员工id：", empId)` 缺占位符的 bug

### 6. 日志级别调整

- `com.sky.mapper`：debug → info，高负载下不再打印每条 SQL

### 7. Nginx 限流（nginx.conf）

```nginx
# 通用限流：单 IP 每秒 20 请求，突发 40
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=20r/s;
# 下单限流：单 IP 每秒 5 请求，突发 10，防刷单
limit_req_zone $binary_remote_addr zone=order_limit:10m rate=5r/s;
# 单 IP 并发连接数限制
limit_conn_zone $binary_remote_addr zone=conn_limit:10m;

location /user/ {
    limit_req zone=api_limit burst=40 nodelay;
    proxy_pass http://webservers/user/;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
}

location /user/order/submit {
    limit_req zone=order_limit burst=10 nodelay;
    proxy_pass http://webservers/user/order/submit;
}
```

## 四、面试要点（高并发 / 高负载治理）

### 1. 为什么要显式配 Druid 连接池？

默认 `maxActive=8` 太小。数据库连接是昂贵资源，连接池用「复用」替代「每次新建/销毁」。合理容量 = 峰值 QPS × 单请求平均持有时长。配太小会阻塞，配太大又拖垮数据库（数据库连接数有限），需压测取平衡。

### 2. 三层限流分别防什么？

| 层 | 手段 | 防什么 |
|----|------|--------|
| Nginx 限流 | `limit_req` 令牌桶 | 恶意刷接口、突发流量打垮后端 |
| 应用层幂等 | submitToken + Redis delete | 重复提交订单 |
| 数据库连接池 | max-wait 超时 | 连接耗尽时快速失败而非雪崩 |

### 3. 为什么限流用令牌桶（burst + nodelay）？

`rate=20r/s` 是稳态速率，`burst=40` 允许突发 40 个，`nodelay` 表示突发请求立即处理不排队。令牌桶既能平滑限流，又能容忍正常突发（如秒杀瞬时流量）。

### 4. 单机扛不住怎么办？（水平扩展）

- 用 `upstream` 配置多实例 + 权重负载均衡（nginx.conf 已预留 8088 节点注释）
- 无状态服务（JWT 而非 session），天然支持多实例横向扩容
- 会话/共享数据放 Redis，实例间共享

### 5. 高负载下日志为什么是瓶颈？

同步日志写磁盘是 I/O 密集操作，高并发下每条 SQL 都打印会拖慢整个请求链路。生产环境应：
- 业务日志 info、SQL 日志 debug（按需临时开）
- 异步日志（logback AsyncAppender）
- 敏感信息（token、密码）脱敏

### 6. 访问容量从哪些维度评估？

- **连接数**：Tomcat 线程、Nginx worker_connections、数据库连接池
- **吞吐**：QPS/TPS，接口耗时（P99）
- **资源**：CPU、内存、JVM GC、数据库慢查询
- **压测**：JMeter/Gatling 定位瓶颈点（本次优化即为针对静态代码审查发现的瓶颈）
