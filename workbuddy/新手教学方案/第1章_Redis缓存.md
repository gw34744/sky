## 第一章：Redis 缓存——从"为什么要缓存"到"三防"

### 1.1 第一步：为什么要缓存？（建立动机）

**生活化比喻**：你是一家奶茶店的老板，店里有一块小黑板。顾客每次来问"珍珠奶茶多少钱一杯"，你有两个选择：

- **方案 A（没有缓存）**：每次都翻厚厚的价目本（查数据库），哪怕答案从没变过；
- **方案 B（有缓存）**：把最常被问的几款价格写在黑板上（缓存），顾客一问就抬头看黑板，秒答。

当顾客很少时，两种方案没区别。但**高峰期**（比如外卖平台大促、午饭时间），如果每个人都让你翻价目本，你（数据库）会累垮。

**这就是缓存的核心价值：把「读多写少」的热点数据，放到一个「读取更快、离业务更近」的地方，减少对数据库的访问压力。**

```
没有缓存：  用户 → 应用 → 数据库（每次都查，慢、压力大）
有缓存：    用户 → 应用 → 缓存(Redis) → 命中直接返回（快）
                              ↓ 未命中
                            数据库（查一次，再回填缓存）
```

### 1.2 第二步：Redis 到底是什么？

**一句话**：Redis 是一个**基于内存的 key-value 存储**，数据存在内存里所以极快（每秒可处理十万级请求），而且支持丰富的数据结构（字符串、哈希、列表、集合、有序集合）。

| 特性 | 说明 | 对项目的意义 |
|------|------|-------------|
| 基于内存 | 数据在 RAM，读写微秒级 | 比 MySQL（磁盘）快几个数量级 |
| key-value | 像一个大 Map | 存 `dish_1` → 菜品列表 |
| 丰富结构 | String/Hash/List/Set/ZSet | 能做缓存、计数器、分布式锁 |
| 支持过期 | 每个 key 可设 TTL | 解决内存膨胀、缓存一致性兜底 |

**为什么要学它**：苍穹外卖里「菜品列表」「套餐列表」「营业状态」这些数据，用户会高频浏览但很少变化，正是缓存的绝佳场景。

### 1.3 第三步：演示案例——最简单的缓存读写

先别急着看项目代码，我们用一个**最小案例**理解「缓存」到底在做什么。

```java
// Demo1：最简单的缓存逻辑（伪代码，先建立直觉）
public String 查询价格(String 商品名) {
    // 第 1 步：先查缓存（Redis）
    String 价格 = redis.get(商品名);
    if (价格 != null) {
        System.out.println("缓存命中！直接返回");
        return 价格;   // 命中缓存，不查数据库
    }

    // 第 2 步：缓存没命中，查数据库
    价格 = 数据库查询(商品名);

    // 第 3 步：把结果写回缓存，下次就命中了
    redis.set(商品名, 价格);

    return 价格;
}
```

**这就是「旁路缓存」（Cache-Aside）模式的雏形，也是最常用的缓存模式。** 它的三步是：`查缓存 → 未命中查库 → 回填缓存`。项目里 `DishController.list` 用的就是它。

> 你可以把这个三步流程背下来，这是所有缓存面试题的起点。

### 1.4 第四步：缓存三大问题（穿透 / 击穿 / 雪崩）

这是缓存面试的**必考题**，也是你项目代码里真实处理了的三个问题。我们用同一个奶茶店比喻串起来理解。

#### 1.4.1 缓存穿透（Penetration）

**生活化比喻**：有人故意问你"有没有 888 元的隐形奶茶"——这东西根本不存在，你翻遍价目本也找不到，但每次都得翻。

**定义**：查询一个**根本不存在的数据**，缓存里没有，数据库里也没有。所以每次请求都会「穿透」缓存，直接打到数据库。

**危害**：恶意构造大量不存在的 key（比如 `dish_99999`），能把数据库打垮。

**解决方案**（项目用了第一种）：
1. **空值缓存**：查库发现是空，也往缓存里存一个「空标记」（短过期时间），下次命中空标记直接返回，不再打库；
2. **布隆过滤器**：用一个数据结构预先判断"这个 key 一定不存在"，直接拦截。

**项目真实代码对照**（`DishController.list` 第 84-90 行）：

```java
if (list == null || list.isEmpty()) {
    // 缓存穿透防护：查库结果为空，缓存一个「空值标记」，短过期时间（5 分钟）
    // 这样恶意构造不存在的分类 id 时，后续请求命中空标记直接返回，不再打库
    redisTemplate.opsForValue().set(key, EMPTY_LIST, EMPTY_TTL_MINUTES, TimeUnit.MINUTES);
    return Result.success(Collections.emptyList());
}
```

#### 1.4.2 缓存击穿（Breakdown）

**生活化比喻**：某款爆款奶茶的价签刚被撕掉（缓存刚好过期），瞬间来了 100 个人同时问价，结果 100 个人全跑去翻价目本（数据库），数据库瞬间被打爆。

**定义**：某个**热点 key 在过期的那一刻**，大量并发请求同时涌入，因为缓存失效了，这些请求**全部**打到数据库。

**关键区别**：击穿是「一个热点 key 过期」引发的，穿透是「key 本来就不存在」。

**解决方案**（项目用了互斥锁）：
1. **互斥锁**：只让一个线程去查库重建缓存，其他线程等待后重读缓存；
2. **逻辑过期**：给热点数据设置"逻辑过期时间"，物理上不过期，后台异步更新。

**项目真实代码对照**（`DishController.list` 第 60-70 行）：

```java
// 缓存未命中，尝试获取互斥锁，防止缓存击穿
String lockKey = "lock_" + key;
try {
    // 自旋重试：抢不到锁说明已有线程在重建缓存，稍等片刻后重读缓存
    while (Boolean.FALSE.equals(
            redisTemplate.opsForValue().setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS))) {
        Thread.sleep(50);
        // 等待期间缓存可能已被重建，重读一次
        list = (List<DishVO>) redisTemplate.opsForValue().get(key);
        if (list != null && list.size() > 0) {
            return Result.success(list);  // 已被重建，直接返回
        }
    }
    // ... 抢到锁的线程去查库重建缓存
```

#### 1.4.3 缓存雪崩（Avalanche）

**生活化比喻**：店里的价签用的都是同一种墨水，某天同时褪色（大量 key 同时过期），所有顾客的问题瞬间全涌向价目本。

**定义**：**大量 key 在同一时刻集中过期**，导致大量请求同时打到数据库，数据库被瞬间压垮。

**解决方案**：
1. **过期时间加随机值**：让 key 的过期时间错开，避免同时失效；
2. **集群高可用**、限流降级等兜底手段。

**项目真实代码对照**（`DishController.list` 第 92-97 行）：

```java
// 写入缓存，并设置随机过期时间：基础 30 分钟 + 0~10 分钟随机值
// 1) 解决缓存无限膨胀占用内存的容量问题
// 2) 随机值避免大量 key 在同一时刻同时过期，防止缓存雪崩
// 3) 过期时间同时作为「缓存与数据库一致性」的兜底手段
long ttl = 30 + ThreadLocalRandom.current().nextInt(10);
redisTemplate.opsForValue().set(key, list, ttl, TimeUnit.MINUTES);
```

#### 1.4.4 三防对比速记表

| 问题 | 触发条件 | 核心解法 | 项目里怎么做 |
|------|---------|---------|-------------|
| 穿透 | 查不存在的 key | 空值缓存 / 布隆过滤器 | 空值标记（5 分钟） |
| 击穿 | 热点 key 过期瞬间 | 互斥锁 / 逻辑过期 | setIfAbsent 互斥锁 + 自旋 |
| 雪崩 | 大量 key 同时过期 | 过期时间随机化 | TTL = 30 + 随机(0~10) 分钟 |

### 1.5 第五步：RedisTemplate vs Spring Cache（两套缓存实现）

项目里「菜品」用 `RedisTemplate` 手动缓存，「套餐」用 Spring Cache 注解，这是黑马刻意设计的对比，也是面试官爱追问的点。

**生活化比喻**：
- `RedisTemplate` 是「手动挡汽车」——每个操作（挂挡、离合）都自己来，控制力强但累；
- `Spring Cache` 是「自动挡汽车」——挂个 D 档（写个注解）就走，省事但细节不可控。

**RedisTemplate 手动缓存**（菜品，`DishController`）：

```java
// 手动三步：查缓存 → 判空 → 查库 → 写缓存
String key = "dish_" + categoryId;
List<DishVO> list = (List<DishVO>) redisTemplate.opsForValue().get(key);
if (list != null && list.size() > 0) return Result.success(list);
// ... 查库
redisTemplate.opsForValue().set(key, list, ttl, TimeUnit.MINUTES);
```

**Spring Cache 注解缓存**（套餐，`SetmealController`）：

```java
@Cacheable(cacheNames = "setmealCache", key = "#categoryId")   // 自动缓存
public Result<List<Setmeal>> list(Long categoryId) { ... }

@CacheEvict(cacheNames = "setmealCache", key = "#setmealDTO.categoryId")  // 自动失效
```

**对比表**：

| 维度 | RedisTemplate 手动 | Spring Cache 注解 |
|------|-------------------|------------------|
| 实现 | 自己写 get/set/delete | 注解声明式，AOP 代理 |
| 代码侵入 | 缓存逻辑混在业务里 | 业务代码干净 |
| key 管理 | 手动拼接 `"dish_" + id` | SpEL 表达式 `#categoryId` |
| 失效 | 手动 `keys(pattern)` + delete | `@CacheEvict` 自动 |
| 灵活性 | 高（能精确控制时机/过期/结构） | 低（受注解能力限制） |

**面试要能讲清的一句话**：两者本质都是「把热点数据从数据库搬到 Redis」，只是封装层级不同。RedisTemplate 是底层 API，Spring Cache 是在它之上的声明式封装。

### 1.6 缓存与数据库的一致性（进阶）

**问题**：数据在数据库里更新了，但缓存里还是旧值，怎么办？

**项目采用「先更新数据库，再删缓存」的旁路缓存策略**：写操作时先更新 DB，再删除对应缓存（或调用 `@CacheEvict`），下次读时缓存未命中会重新查库回填，从而拿到最新值。

```
写操作：更新数据库 → 删除缓存
读操作：查缓存 → 未命中查库 → 回填缓存
```

**为什么是「删缓存」而不是「更新缓存」**：删缓存更简单，避免了「更新缓存值算错」的风险，靠「下次读时回填」来保证最终一致，配合过期时间兜底。

### 1.7 Redis 序列化（一个隐藏的坑）

**问题**：Redis 存 value 时，默认用 JDK 序列化，存进去是 `\xAC\xED...` 这样的二进制，用 `redis-cli` 看是一堆乱码，没法排查，还要求实体类实现 `Serializable`。

**项目修复**（`RedisConfiguration`）：key 用 `StringRedisSerializer`，value 用 `GenericJackson2JsonRedisSerializer`（JSON 格式 + 类型信息）。

```java
redisTemplate.setKeySerializer(new StringRedisSerializer());
redisTemplate.setValueSerializer(new GenericJackson2JsonRedisSerializer());
```

**好处**：value 变成可读的 JSON、跨语言可用、实体类不用实现 Serializable。
