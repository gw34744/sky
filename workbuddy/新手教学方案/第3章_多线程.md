# 第三章：多线程——一切并发问题的地基

> 这是三个主题里最基础、也最重要的一章。前面讲的「缓存击穿（并发打到数据库）」「事务并发问题（脏读/幻读）」「状态机并发（重复接单）」**根源都是多线程**。把这章学透，前面很多"为什么"会豁然开朗。

---

## 3.1 第一步：什么是线程？为什么要多线程？

**生活化比喻**：一家餐厅只有 1 个厨师（单线程），来 10 个客人，只能一个一个做菜，后面的客人等到崩溃。如果雇 10 个厨师（多线程），可以同时做 10 道菜。

**核心概念**：
- **进程**：一个正在运行的程序（比如你的 Java 应用），是资源分配的最小单位；
- **线程**：进程内部的一条执行路径，是 CPU 调度的最小单位。一个进程可以有多个线程。

**为什么要多线程**：让程序"同时"做多件事，提高 CPU 利用率和响应速度。

**但多线程是有代价的**——多个线程同时访问同一份数据，会引发「线程安全」问题。这就是本章的重点。

## 3.2 第二步：多线程的核心问题——共享数据的并发安全

**生活化比喻**：两个厨师（两个线程）同时往同一个锅里（共享变量）加盐，都先看了下"当前盐量是 5 克"，然后都加 1 克，结果锅里的盐是 6 克，而不是应该的 7 克——因为他们的"看"和"加"不是原子的。

**演示案例（必跑）**：

```java
// Demo3：多线程共享变量的经典 bug
public class CounterDemo {
    static int count = 0;   // 共享变量

    public static void main(String[] args) throws InterruptedException {
        // 起 100 个线程，每个线程给 count 加 1000 次
        Thread[] threads = new Thread[100];
        for (int i = 0; i < 100; i++) {
            threads[i] = new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    count++;   // ❌ 这行不是原子操作！
                }
            });
            threads[i].start();
        }
        // 等所有线程跑完
        for (Thread t : threads) t.join();

        // 期望 100 * 1000 = 100000，但实际结果会小于这个数
        System.out.println("期望值：100000，实际值：" + count);
    }
}
```

**运行结果**：几乎每次运行，`count` 都会小于 100000（比如 97843、99120 等），而且每次结果还不一样。

**为什么**：`count++` 表面是一行，底层其实是三步——「读 count → 加 1 → 写回 count」。两个线程可能同时"读"到相同的值，再各自加 1 写回，导致一次加法丢失。这就是**竞态条件（Race Condition）**。

> 这个案例是理解后面所有锁、原子类、synchronized 的起点。**先亲手跑出这个 bug，再学解法，印象最深。**

## 3.3 第三步：解决并发安全——synchronized 和 volatile

### 3.3.1 synchronized：互斥锁

**思路**：让「读-改-写」变成原子操作，同一时刻只允许一个线程进入临界区。

```java
// 修法 1：用 synchronized 给方法加锁
static int count = 0;

static synchronized void increment() {  // 同一时刻只有一个线程能进这个方法
    count++;
}

// 调用处改成 increment();
```

**关键词解释**：`synchronized` 是 Java 内置的互斥锁，保证同一时刻只有一个线程执行被锁住的代码块。多个线程会排队依次进入。

### 3.3.2 volatile：保证可见性

**问题**：每个线程可能有自己的"工作内存"（CPU 缓存），线程 A 改了变量，线程 B 可能看不到。

**`volatile` 的作用**：保证变量的修改**对所有线程立即可见**（强制从主内存读写），并禁止指令重排序。

```java
static volatile boolean flag = false;   // 加 volatile 保证可见性
```

**但注意**：`volatile` 只保证「可见性」，**不保证「原子性」**。`count++` 这种「读-改-写」操作，光用 volatile 还是不对的（因为它还是三步）。所以：
- 简单读写（如开关标志位）→ 用 `volatile`；
- 复合操作（如 `count++`）→ 用 `synchronized` 或原子类。

### 3.3.3 原子类（AtomicInteger）：更优雅的解法

```java
import java.util.concurrent.atomic.AtomicInteger;

static AtomicInteger count = new AtomicInteger(0);

// 调用处：count.incrementAndGet();   // 原子地 +1，底层用 CAS 实现
```

**原子类**内部用 **CAS（Compare-And-Swap，比较并交换）** 实现无锁的原子操作，性能比 synchronized 好。

**CAS 一句话解释**：修改前先比较「当前值是不是我预期的那旧值」，是才改，不是就重试。这就是前面状态机一章提到的「乐观锁」的底层原理。

## 3.4 第四步：ThreadLocal——每个线程自己的"私人物品柜"

### 3.4.1 它解决什么问题

**生活化比喻**：公司前台有一个公共储物柜，但每个员工都需要存自己的东西。如果都放同一个格子就乱了。**ThreadLocal 就是给每个线程分配一个"私人储物柜"**，各存各的，互不干扰。

**定义**：`ThreadLocal` 让每个线程都拥有一份独立的变量副本，线程之间互不影响。

### 3.4.2 项目真实代码：BaseContext

你项目里 `BaseContext` 就是用 ThreadLocal 存「当前登录用户 ID」：

```java
public class BaseContext {
    // 每个线程独立的 ThreadLocal，存自己的用户ID
    public static ThreadLocal<Long> threadLocal = new ThreadLocal<>();

    public static void setCurrentId(Long id) { threadLocal.set(id); }   // 存入
    public static Long getCurrentId() { return threadLocal.get(); }     // 取出
    public static void removeCurrentId() { threadLocal.remove(); }      // 清理（重要！）
}
```

**为什么用它**：一次 HTTP 请求从「拦截器 → Controller → Service」全程在同一个线程里跑，把 userId 放进 ThreadLocal，后续任何层都能直接 `getCurrentId()` 拿到，不用一层层传参。

**这也解释了一个前面的 bug**：支付回调是微信服务器主动调用的，走的是**另一个线程**，那个线程的 ThreadLocal 里根本没有 userId，所以 `getCurrentId()` 返回 null——这就是「支付回调依赖登录态」bug 的根源。**理解 ThreadLocal，你就彻底懂了这个 bug。**

### 3.4.3 ThreadLocal 的两大坑（面试必背）

**坑 1：内存泄漏——用完必须 remove**

ThreadLocal 的 key 是弱引用，但 value 是强引用。线程（尤其线程池里的线程）长期存活时，如果不 `remove()`，value 会一直被引用，导致内存泄漏。

```java
// ❌ 不清理，线程复用后读到残留数据，或内存泄漏
// ✅ 正确做法：finally 里 remove
try {
    BaseContext.setCurrentId(userId);
    // ... 业务
} finally {
    BaseContext.removeCurrentId();
}
```

**坑 2：跨线程丢失**——ThreadLocal 数据只在当前线程有效，子线程（`@Async`、MQ 消费、线程池）拿不到。这正是上一份报告里「MDC traceId 跨线程传递」要解决的问题（用 TaskDecorator 手动把值传给子线程）。

## 3.5 第五步：线程池——为什么要池化？

**生活化比喻**：每来一个任务就"招一个临时工"（new Thread），任务结束就"辞退"，频繁招人辞人成本极高。**线程池就是"固定雇一批常驻员工"**，任务来了分配，任务完了回收，避免频繁创建销毁线程的开销。

**核心概念**：线程池维护一组常驻线程 + 一个任务队列，复用线程执行任务。

**关键参数**（对应你项目里的 `AsyncConfiguration`）：

```java
executor.setCorePoolSize(5);      // 核心线程数：常驻，不轻易销毁
executor.setMaxPoolSize(10);      // 最大线程数：高峰时扩容上限
executor.setQueueCapacity(200);   // 队列容量：核心线程忙时任务先排队
executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy()); // 拒绝策略
```

**执行流程**（面试必背）：
```
任务来了 → 核心线程没满？直接用核心线程
        → 核心线程满了？进队列排队
        → 队列也满了？扩容到最大线程数
        → 最大线程也满了？走拒绝策略（CallerRunsPolicy = 由调用线程执行）
```

### 3.5.1 Spring 的 @Async

`@Async` 让方法变成**异步执行**（扔给线程池，主线程立即返回，不等待结果）。

```java
@Async("asyncExecutor")   // 指定用哪个线程池
public void sendEmail() {
    // 这个方法的执行被扔到线程池，调用方不等待
}
```

**两个坑（面试必背）**：
1. `@Async` 方法**不能是 private**（代理拦截不到）；
2. 调用方和目标方法要**在不同 Bean**（同类内部自调用不走代理，和 `@Transactional` 失效是同一个道理）。

## 3.6 第六步：并发工具——CountDownLatch 和 AtomicReference

这两个工具在项目的「缓存击穿并发测试」里真实用到了，理解它们你就能读懂那个测试。

### 3.6.1 CountDownLatch：让线程"同时起跑"或"等所有跑完"

**生活化比喻**：赛跑发令枪。所有运动员就位后（`ready.countDown()`），裁判一声令下（`start.countDown()`），大家同时起跑；跑完后裁判等所有人到终点（`done.await()`）。

```java
CountDownLatch ready = new CountDownLatch(10);  // 等 10 个线程就位
CountDownLatch start = new CountDownLatch(1);   // 发令枪
CountDownLatch done = new CountDownLatch(10);   // 等 10 个线程跑完

// 每个线程：ready.countDown() 就位 → start.await() 等发令 → 干活 → done.countDown()
// 主线程：ready.await() 等就位 → start.countDown() 发令 → done.await() 等跑完
```

**用途**：并发测试里保证 10 个线程「真的同时」发起请求，否则串行跑就测不出击穿问题。

### 3.6.2 AtomicReference / AtomicInteger：原子的变量

- `AtomicInteger`：原子的 int（前面讲过）；
- `AtomicReference<T>`：原子的「对象引用」，配合 `compareAndSet` 实现无锁更新。

```java
AtomicReference<List<DishVO>> cache = new AtomicReference<>();
// 原子的比较并设置：只有当当前值是预期值 oldValue 时才更新为新值
cache.compareAndSet(oldValue, newValue);
```

## 3.7 第七步：把多线程和前面串起来（重要！）

学到这里，你应该能重新理解前面几个"为什么"了：

| 现象 | 多线程底层原因 |
|------|--------------|
| 缓存击穿 | 热点 key 过期，多线程并发打到数据库 |
| 缓存击穿的锁 `setIfAbsent` | 用 Redis 的原子操作实现"互斥"，只让一个线程查库 |
| 事务并发问题（脏读等） | 多个事务（线程）同时操作同一批数据 |
| 状态机并发重复接单 | 两个线程同时校验状态都通过，重复更新 |
| 支付回调拿不到 userId | 回调是另一个线程，ThreadLocal 不跨线程 |
| MDC traceId 跨线程丢失 | ThreadLocal 数据不自动传给子线程 |

**一句话总结这一章**：多线程让程序高效，但引入「共享数据并发安全」问题；解决手段有锁（synchronized）、原子类（CAS）、ThreadLocal（线程隔离）、线程池（资源复用）、并发工具（CountDownLatch）。
