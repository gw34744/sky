# 第二章：事务与并发——从"ACID"到"为什么下单必须原子"

> 这一章要解决的问题：为什么 `submitOrder` 方法上必须加 `@Transactional`？"事务"到底在保护什么？以及高并发下订单号为什么不能用时间戳？

---

## 2.1 第一步：为什么需要事务？（建立动机）

**生活化比喻**：你去银行转账，从 A 账户转 100 元到 B 账户，内部其实有两步：

1. A 账户余额 - 100；
2. B 账户余额 + 100。

**如果系统只执行了第 1 步就崩溃了**，会怎样？A 的钱没了，B 的钱也没到账——**凭空消失了 100 元**。这是绝对不允许的。

**事务就是来解决这个问题的**：它保证「一组操作要么全部成功，要么全部失败（回滚）」，不会出现"做了一半"的中间状态。

**对应到你的项目**：`submitOrder` 下单方法内部有 3 步数据库写操作：

```
第 1 步：插入订单表（orders）
第 2 步：批量插入订单明细表（order_detail）
第 3 步：清空购物车
```

如果第 1 步成功、第 2 步失败，就会产生「**有订单但没有明细**」的脏数据——这就是为什么这个方法的原始代码是一个**真实的 bug**（缺少事务保护）。

## 2.2 第二步：核心概念——ACID

事务有四个特性，英文首字母缩写 **ACID**：

| 特性 | 英文 | 一句话解释 | 生活化比喻 |
|------|------|-----------|-----------|
| 原子性 | Atomicity | 要么全做，要么全不做 | 转账两步必须同时成功 |
| 一致性 | Consistency | 事务前后数据都符合规则 | 转账前后总额不变 |
| 隔离性 | Isolation | 并发事务互不干扰 | 别人转账不影响我 |
| 持久性 | Durability | 提交后永久保存 | 钱到账了不会丢 |

> **面试常问**：「讲讲 ACID」「为什么下单必须保证原子性」。你现在应该能答出来了：因为订单、明细、购物车是强关联数据，任何一步失败都必须整体回滚，否则产生脏数据。

## 2.3 第三步：@Transactional 是什么？怎么用？

Spring 提供了 `@Transactional` 注解，只要加在方法上，Spring 就会自动为这个方法开启事务：方法正常执行完就「提交」，抛出异常就「回滚」。

```java
@Transactional   // 加上这个注解，方法内的数据库操作就变成一个事务
public OrderSubmitVO submitOrder(OrdersSubmitDTO ordersSubmitDTO) {
    // 第 1 步：插订单
    orderMapper.insert(order);
    // 第 2 步：插明细
    orderDetailMapper.insertBatch(orderDetails);
    // 第 3 步：清购物车
    shoppingCartMapper.deleteByUserId(userId);
    // 方法正常返回 → 事务提交；任何一步抛异常 → 全部回滚
    return orderSubmitVO;
}
```

**关键认知**：`@Transactional` 是通过 **AOP 代理** 实现的。Spring 会给你的类包一层"代理对象"，代理对象在调用你真正的方法前开启事务、方法结束后提交/回滚。

### 2.3.1 事务失效的四大坑（面试必背）

这是面试最爱追问的，也是"许愿式开发"最容易忽略的：

**坑 1：自调用（同类内部方法互调）**

```java
public void methodA() {
    this.methodB();  // ❌ 直接 this 调用，绕过了代理，事务不生效！
}

@Transactional
public void methodB() { ... }
```

**为什么失效**：`@Transactional` 靠代理对象拦截，但 `this.methodB()` 是直接调用自身，根本没经过代理，所以事务不会开启。

**坑 2：异常被吞掉（catch 后不抛出）**

```java
@Transactional
public void method() {
    try {
        // 抛异常的数据库操作
    } catch (Exception e) {
        // ❌ 吞掉异常，事务感知不到，不会回滚！
        log.error("出错了", e);
    }
}
```

**为什么失效**：事务靠"抛出异常"来触发回滚，你把异常 catch 掉了，事务以为一切正常，就提交了。

**坑 3：非 public 方法**

```java
@Transactional
private void method() { ... }  // ❌ private 方法，代理无法拦截，事务失效
```

**坑 4：异常类型不对**

默认只有 `RuntimeException`（运行时异常）和 `Error` 会触发回滚，受检异常（checked exception）默认不回滚。要用 `@Transactional(rollbackFor = Exception.class)` 指定。

### 2.3.2 演示案例：手动模拟事务回滚

不用连数据库，我们用伪代码 + 打印，直观理解"提交"和"回滚"：

```java
// Demo2：理解事务的提交与回滚
public void 转账(boolean 模拟异常) {
    System.out.println("=== 事务开始 ===");
    try {
        账户A扣钱();          // 操作1
        System.out.println("操作1 完成：A 扣 100");

        if (模拟异常) {
            throw new RuntimeException("操作2 失败！");  // 模拟第2步出错
        }

        账户B加钱();          // 操作2
        System.out.println("操作2 完成：B 加 100");

        System.out.println("=== 事务提交：两步都成功 ===");
    } catch (Exception e) {
        // 关键：这里回滚，把操作1也撤销
        System.out.println("=== 事务回滚：撤销操作1，A 的钱回来了 ===");
    }
}
```

**运行结果**：
- `转账(false)`：提交，A 扣 100、B 加 100；
- `转账(true)`：回滚，操作 1 被撤销，A 的钱恢复。

**这就是 @Transactional 在背后替你做的事**——你不用自己写 try/catch，Spring 代理帮你完成了"异常则回滚"的逻辑。

## 2.4 第四步：事务隔离级别与并发问题

当**多个事务同时操作同一批数据**时，会产生并发问题。这是"事务"和"多线程"交叉的地方（也是为什么第三章要先讲多线程）。

### 2.4.1 四大并发问题

| 问题 | 英文 | 一句话解释 |
|------|------|-----------|
| 脏读 | Dirty Read | 读到了别人"未提交"的数据（可能被回滚） |
| 不可重复读 | Non-repeatable Read | 同一事务两次读，结果不一样（别人改了） |
| 幻读 | Phantom Read | 同一事务两次查询，行数变了（别人插了） |
| 丢失更新 | Lost Update | 两个事务同时改，后提交的覆盖了先提交的 |

### 2.4.2 四大隔离级别（层层递进）

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|---------|------|-----------|------|------|
| 读未提交 READ UNCOMMITTED | ✗ | ✗ | ✗ | 最高 |
| 读已提交 READ COMMITTED | ✓ | ✗ | ✗ | 高 |
| 可重复读 REPEATABLE READ（MySQL 默认） | ✓ | ✓ | ✗ | 中 |
| 串行化 SERIALIZABLE | ✓ | ✓ | ✓ | 最低 |

> ✗ 表示「可能出现该问题」，✓ 表示「已解决」。
> **MySQL 默认是「可重复读」（REPEATABLE READ）**，这是常考的点。

**面试能讲清的一句话**：隔离级别越高，数据越安全，但并发性能越低，是在「安全性」和「性能」之间做权衡。

## 2.5 第五步：并发唯一性——雪花算法

### 2.5.1 问题：为什么订单号不能用时间戳？

**原始代码**：`order.setNumber(String.valueOf(System.currentTimeMillis()))`

**生活化比喻**：用"现在几点几分几秒"当你的学号。如果两个同学在同一秒内报到，他们的学号就撞了。

**问题所在**：`System.currentTimeMillis()` 返回毫秒时间戳，但**高并发下，同一毫秒内可能有多个请求同时下单**，它们会拿到完全相同的时间戳，导致订单号重复（撞号）。

### 2.5.2 解决方案：雪花算法（Snowflake）

雪花算法生成的 ID 是 64 位二进制，拆成四段：

```
┌─┬───────────────────┬──────────────┬─────────────┬──────────────┐
│0│  41位时间戳        │ 10位机器标识  │ 5位数据中心  │ 12位序列号    │
└─┴───────────────────┴──────────────┴─────────────┴──────────────┘
 符号  毫秒级(69年)      1024个节点      32个        同毫秒4096个
```

- **41 位时间戳**：保证趋势递增（利于数据库索引）；
- **10 位机器标识**：区分不同机器，保证分布式唯一；
- **12 位序列号**：同一毫秒内最多生成 4096 个不同 ID，解决"同一毫秒撞号"问题。

**三个特性**：趋势递增（利于索引）、分布式唯一、无第三方依赖（不用连 Redis/数据库）。

**项目真实代码**（`SnowflakeIdUtil`，你项目里已经写好了）：

```java
public static synchronized long nextId() {
    long timestamp = currentTimeMillis();
    // 时钟回拨检测：系统时钟被回拨会导致 ID 重复，直接抛异常
    if (timestamp < lastTimestamp) {
        throw new RuntimeException("时钟回拨，拒绝生成ID");
    }
    // 同一毫秒内，序列号自增（+1）
    if (timestamp == lastTimestamp) {
        sequence = (sequence + 1) & MAX_SEQUENCE;
    } else {
        sequence = 0L;   // 不同毫秒，序列号归零
    }
    lastTimestamp = timestamp;
    // 拼接：时间戳 | 数据中心 | 机器ID | 序列号
    return ((timestamp - START_TIMESTAMP) << TIMESTAMP_SHIFT)
            | (DATA_CENTER_ID << DATA_CENTER_ID_SHIFT)
            | (WORKER_ID << WORKER_ID_SHIFT)
            | sequence;
}
```

### 2.5.3 雪花算法 vs UUID（面试对比）

| 方案 | 是否递增 | 对索引影响 | 说明 |
|------|---------|-----------|------|
| 雪花算法 | 趋势递增 | 利于 B+ 树插入 | 推荐 |
| UUID | 完全随机 | 导致页分裂、性能差 | 不推荐做主键 |

**为什么递增对数据库重要**：MySQL 的 InnoDB 用 B+ 树组织主键，主键递增时新数据总是追加到末尾，效率高；UUID 随机则会导致频繁"页分裂"，性能下降。

## 2.6 第六步：订单状态机的并发问题（承上启下）

状态机（上一份报告里讲过）解决了「状态流转是否合法」的问题，但**没解决并发问题**：

**场景**：两个并发请求同时把订单从「待接单」转到「已接单」，状态机校验会**都通过**，导致重复接单。

**解决方案**（面试可讲）：
1. **乐观锁**：`update orders set status = 新值 where id = ? and status = 旧值`，用影响行数判断是否被并发修改（行数为 0 说明已被别人改过）；
2. **分布式锁**；
3. **条件更新（CAS）**。

> 这一节引出了「乐观锁 / CAS」的概念，它在第三章多线程里会详细展开，两者是相通的。
